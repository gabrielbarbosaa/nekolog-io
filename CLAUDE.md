## What NekoLog is

An open-core logging platform for JS/TS apps (frontend + backend): npm SDKs that batch-send logs, an ingestion API, ClickHouse for storage, background jobs for alerts, and a dashboard with search/filters/charts/alerts, with separate API keys per environment (`nekolog_pk_…` public, `nekolog_sk_…` secret — the key determines the environment, SDKs never pass one explicitly).

It's a personal/portfolio project designed to run entirely on free-tier cloud services (Cloudflare Workers/KV/R2/Tunnel, Oracle Always Free VM for ClickHouse, Neon Postgres, Upstash Redis, Vercel, Resend). The SDKs, ingestion, jobs, and public read API are self-hostable via a single `docker-compose`; **the dashboard is not** — it's closed-source and cloud-only (see "Two repositories" above). The only paid cost is the `nekolog.io` domain.

### Architecture at a glance

```
SDKs (browser / node) → HTTPS batch (gzip)
   → Cloudflare Worker "ingest" (Hono) → KV (key→project/env/quota) → ClickHouse (via Tunnel, on Oracle VM)
   Cloudflare Worker "jobs" (cron, 1 min) → alerts/issues/usage/quotas → Resend/Slack/Discord/webhook
   Vercel: Next.js dashboard (closed-source, deployed from the separate nekolog-dashboard repo)
      → Neon Postgres (users/orgs/projects/keys/alerts), Upstash Redis (auth), Resend
   Cloudflare R2: source maps
```

Key invariants from `docs/PLANO.md` §3–4 that should guide any implementation:

- **Ingestion does no I/O beyond the write; processing happens elsewhere.** The ingest API validates, derives what comes out of the event itself, and writes. Anything needing a network call or a database read — source-map resolution, alert evaluation, issue building — runs in `apps/jobs`. **Fingerprinting is computed at ingestion** (spec 5, step 4.5): it is pure CPU over the event in hand, and ClickHouse cannot backfill the `fingerprint` column after the insert without a mutation. `docs/PLANO.md` §3 principle 1 states the rule in this form; an older wording said error grouping ran outside ingestion, which contradicted spec 5 and `ETAPAS.md` 4.5 and was settled in favour of ingestion on 2026-10-31.
- **Ingestion never depends on Postgres or Redis** — keys live in Workers KV so Neon's cold-start/hibernation never adds latency to the hot path.
- **Vendor-specific behavior is always behind an interface** (`KeyStore`, `RateLimiter`, `BlobStore`, `Mailer`, `LogStore`, `RedisClient` in `packages/adapters/`) so the same code runs on free-tier cloud and in self-host (Redis/Valkey, Garage, SMTP, local ClickHouse/Postgres).
- **The SDK must never throw into the host app** and ships with zero dependencies.
- Uses OpenTelemetry-style log shape and W3C `traceparent` propagation.
- **Privacy-by-default (LGPD):** sensitive fields are stripped client- and server-side; raw IPs are never stored, only resolved country.

## Commands that work today

- `pnpm install` — install everything (pnpm 12 via Corepack; `minimumReleaseAge` in `pnpm-workspace.yaml` will refuse packages published too recently — this is intentional, not a bug).
- `pnpm dev` — starts the dev `docker-compose` stack (ClickHouse on :8123, Postgres on :5432, Valkey on :6379, Mailpit on :8025 web UI, Garage S3 on :3900 and its admin API on :3903) and then `turbo run dev`, which also starts `apps/web` on :3000 (Turbopack) and `apps/docs` on :4321/docs (Astro). Copy `.env.example` to `.env` first. `pnpm dev:infra:down` / `pnpm dev:infra:logs` manage the docker stack directly. **Verified working end to end on 2026-10-30**, including an S3 round trip against Garage. Garage replaced MinIO, which withdrew its public images — see ADR [0013](docs/adr/0013-garage-no-lugar-do-minio.md); its credentials have a strict format (`GK` + 24 hex, secret of exactly 64 hex) that `deploy/garage-init.sh` checks and explains.
- `pnpm lint` / `pnpm typecheck` / `pnpm test` / `pnpm build` — Turborepo tasks fanning out to every package's own script (currently `apps/web`, `apps/docs`, `packages/config`, `internal/schema`, `packages/adapters` define some). A package with no matching script is silently skipped by Turbo — that's expected, not a failure. `apps/docs` deliberately has **no** `typecheck` script: `astro check` doesn't support TypeScript 7 and Astro is deprecating it — `astro build` validates the content schemas instead (see `apps/docs/README.md`).
- `apps/web` (landing page) locale: resolved from a `NEKOLOG_LOCALE` cookie, falling back to `Accept-Language`, falling back to `en` (see `apps/web/i18n/request.ts`) — no `/[locale]/` URL prefix. This mirrors the approach the dashboard repo should use too, since `docs/PLANO.md` §10.1's route map never puts locale in the path. The in-page `LocaleSwitcher`/`ThemeToggle` components are temporary proof-of-wiring from step 0.11, not final landing-page UI.
- `pnpm ch:status` / `pnpm ch:migrate` / `pnpm ch:new <name>` — the ClickHouse migration runner in `packages/clickhouse` (spec 3). Forward-only, one SQL command per file in `packages/clickhouse/migrations/`, checksummed in a `_migrations` table; it halts on an edited migration, a gap in the numbering, an out-of-order apply, or a migration the database remembers but the repo no longer has. It never creates the database. The CLI runs `.ts` directly on Node 24 — no build. Its integration tests hit the real ClickHouse on :8123 and are skipped (with a stderr notice) when nothing answers; CI sets `CLICKHOUSE_TEST_REQUIRED=1` so a skip there is a failure instead. See `packages/clickhouse/README.md`.
- The dev ClickHouse has **four users with separate grants** (`deploy/clickhouse-users.dev.xml`, mounted into `users.d/` so it applies on restart without wiping the volume): `nekolog_reader`, `nekolog_ingest`, `nekolog_jobs`, `nekolog_migrator`. Note that `nekolog_ingest` is *not* INSERT-only — ClickHouse requires `SELECT` on the columns a materialized view reads, and without it the INSERT lands in `logs`, fails to feed the view, and returns an error. It therefore holds column-scoped `SELECT` on the six columns the two views read (`project_id`, `environment_id`, `timestamp`, `received_at`, `level`, `service`), and nothing more (see `docs/PLANO.md` §7 and threats E10/E11). **Adding a materialized view means widening that grant before the migration runs** — in dev the mounted file hot-reloads without a restart, but anywhere else the order is the deployer's job.
- **There are two rollups and they answer different questions.** `logs_per_minute` groups by the client-supplied `timestamp` and feeds the charts; `usage_per_minute` groups by the server-stamped `received_at` and feeds usage and quota. Quota must never be computed from `logs_per_minute`: a sender could backdate its events and never appear in today's count (threat T7). `apps/jobs/tests/quota.integration.test.ts` pins this with a real 2020-dated event.
- **Published packages build with `tsdown` and must set `isolatedDeclarations: true`** (see `packages/core/tsconfig.json`). TypeScript 7 no longer exposes the classic API that tsdown's `.d.ts` generator used, so declarations are emitted by Oxc instead — which requires explicit type annotations on exported values whose type can't be inferred syntactically (`export const MAX_MESSAGE_BYTES: number = 16 * 1024`). Don't "fix" those annotations by removing them. Each package's `lint` script runs `publint` and `@arethetypeswrong/cli` against the built output.
- **`@nekolog-io/core` has zero runtime dependencies by contract**, so it cannot import `@internal/schema` (which pulls in Valibot). The payload limits are deliberately duplicated in `packages/core/src/limits.ts`; `packages/core/src/contract.test.ts` compares them one by one against `@internal/schema` and runs the logger's own events through the real ingestion parser, so the duplication cannot drift silently. Keep that test passing rather than deleting the duplication.
- **There are two kinds of published package here, and they resolve differently in the workspace.** The SDKs (`core`, `node`) point `exports` straight at `dist/`: a workspace dependent resolves them through the built output, not the source, so after changing `packages/core` run `pnpm --filter @nekolog-io/core build` before typechecking `packages/node` or you'll see stale types (Turbo's `typecheck`/`test`/`lint` all `dependsOn: ["^build"]`, so CI is fine). The shared internals (`adapters`, `clickhouse`, `config`) instead keep `exports` on `./src/*.ts` and declare the `dist/` mapping under **`publishConfig`**, which `pnpm pack` applies at publish time. That is deliberate: these are run from source inside this repo — `pnpm ch:migrate`, `pnpm seed` and `pnpm --filter @apps/ingest serve` all load them as `.ts` with no build step, and pointing `exports` at `dist/` would quietly break that. The cost is that `publint`/`attw` must inspect the **packed tarball** rather than the directory, which is why each `lint` script runs `pnpm pack --out package.tgz` first. Don't "simplify" either pattern into the other without reading this.
- **`@nekolog-io/db` publishes its TypeScript source as its types, and that is not an oversight.** `pgTable(...)` returns a `PgTableWithColumns<…>` nobody writes by hand, so `isolatedDeclarations` — which TypeScript 7 forces on anything with generated declarations — is not an option. `publishConfig.types` points at `./src/index.ts` and the source ships in the tarball. The consequence is a rule: **the published `src/index.ts` imports no sibling file**, because the consumer compiles it with its own `tsconfig` and a `./tables.ts` import would need their `allowImportingTsExtensions`. `internal/deploy/src/packaging.test.ts` fails if a relative import appears there.
- **Every outgoing e-mail is checked before the network call, and the allowlist fails closed.** `assertMessage` refuses a `\r`, `\n` or null byte in the recipient or subject — that is how an unseen `bcc:` is forged — and demands a single lowercased address, so display names, commas and angle brackets are out. Both `resendMailer` and `smtpMailer` run it *before* dispatching, with a test proving nothing reached `fetch` or the transport. `allowlistedMailer` enforces `EMAIL_ALLOWLIST` in dev and qa and **an empty list allows nobody**: a missing variable is a fresh machine, not permission to write to strangers. Entries match an address exactly or a domain through a leading `@`, so a `+tag` or a lookalike domain does not slip through.
- **The Redis adapters take no dependency on a vendor and run Lua by hash.** `upstashRedis({url, token})` needs only `fetch`; `nodeRedis(client)` takes an ioredis-shaped object the caller injects, the way `kvKeyStore` takes a KV binding — so `@nekolog-io/adapters` still has zero runtime dependencies and still bundles into a Worker. Both cache the SHA from `SCRIPT LOAD` and call `EVALSHA`, falling back to the text only on `NOSCRIPT`; Upstash's free tier counts commands and the OTP script is dozens of lines. An error that is not `NOSCRIPT` is rethrown, so a replica's `READONLY` cannot be mistaken for a missing script. `prefixedRedis` namespaces the `KEYS` of an `eval` but **not** its `ARGV` — an argument is data, not an address — and there is a test for each half.
- **`pnpm-workspace.yaml` overrides `esbuild@<0.25.0` and that is a security fix, not tidying.** `drizzle-kit` reaches the deprecated `@esbuild-kit/*` loaders, which pin esbuild 0.18.20 — vulnerable to GHSA-67mh-4wv8-2f99. The `dependency-review` workflow fails the PR on it, which is the gate working. The override forces a patched esbuild, drizzle-kit still reads the TypeScript schema, and `packages/db`'s tests (which shell out to it) prove it. Don't drop the override without checking that advisory again.
- **The database rules live in the schema, not only in the code that writes to it.** Two repositories write to this Postgres, so `packages/db` carries check constraints — id prefixes, lowercase e-mail, SHA-256-shaped key hashes, a public key that may only write, an invite that cannot grant ownership, a country instead of an address in the audit log. Deleting an organization cascades to projects, environments and keys; deleting a user only nulls `audit_log.actor_user_id`. `packages/db/src/schema.integration.test.ts` applies **the shipped `.sql`** to a throwaway database and tries to violate each rule, so it tests the file that runs rather than the Drizzle object. `migrations.test.ts` regenerates with drizzle-kit and fails if the schema changed without `pnpm db:generate` — without it, editing `src/index.ts` alone changes nothing that runs.
- **The shared internals are ESM-only** (`format: ['esm']`, `attw --profile esm-only`). Their consumers are Node 24, Workers and Next — all ESM — and the migration runner uses `import.meta.url` to find `migrations/`, which has no honest CJS equivalent. The `esm-only` profile is what makes `attw`'s "a require call resolved to an ESM file" warning an expected result instead of a failure.
- **`packages/clickhouse` has three entry points** — the root (which pulls `node:fs` through the migration runner), `/client`, and `/log-store`. A Worker must import one of the subpaths, not the root. Don't collapse them back into one entry to "simplify".
- **The ClickHouse inserts set `input_format_skip_unknown_fields=0`** (`packages/clickhouse/src/log-store.ts`). Without it ClickHouse accepts a row carrying a column the table does not have, writes the rest with defaults and answers success — silent data loss on any schema drift. The price is that a migration must be applied before code that writes a new column, which the forward-only runner already implies.
- **`@nekolog-io/node`'s process hooks are tested against real spawned Node processes** (`packages/node/tests/`), not just a fake `process`, because the failure mode being guarded against (a listener that stops Node from crashing, turning a dead service into a zombie) only shows up in a real process. The fixtures are run directly as `.ts` by Node 24's type stripping, so they need no build. One test is skipped on Windows with a stderr notice — `process.kill(pid, 'SIGTERM')` terminates the process there instead of delivering the signal to a listener; CI runs on Linux, where it does run.
- **The ClickHouse deduplication token is `<environmentId>:<batchId>`, not the bare `batchId`** (`internal/spool/src/envelope.ts`). `batchId` is chosen by the client and ClickHouse deduplicates per table partition, which every project shares — an unscoped token lets one tenant's batch silently suppress another's. Don't "simplify" it back.
- **The rate limit and the attribute budget are per-isolate, by design, and the docs say so.** A Cloudflare Worker runs many isolates, so the in-memory limiter's real ceiling is the configured one times the instance count — it is a burst brake, not a volume control. The daily quota in KV is the actual cap. Don't "fix" either by claiming a guarantee they can't make.
- **The quota task must never treat "I can't measure" as "nobody is over".** If the ClickHouse usage query fails, `quota-block` returns without touching KV; computing an empty block list there would unblock every tenant during an outage. There's a test for it.
- **`quota-block` writes KV only when the set of blocked environments changes**, and keeps every block in one `quota:blocks` document. The free tier allows 1,000 writes and 1,000 list operations per day while the cron wakes 1,440 times, so per-environment keys or an unconditional write would exhaust the quota on their own.
- **`apps/jobs` decides cadence from the cron's `scheduledTime`, never from remembered state** (`(minute - offsetMinutes) % everyMinutes === 0`). A Worker isolate does not survive between runs, so a "last run" variable would work locally and misfire in production. The jobs app also exposes **no route that runs a task** — only `GET /health` — and `apps/jobs/src/app.test.ts` fails if one is added (threat E12). Don't add a `/run` endpoint for convenience.
- `pnpm check` — `biome check --write .` (formats + lints; excludes `**/*.md` and lockfiles — see `biome.json`). CI instead runs `biome ci .` (no writes).
- `pnpm seed init` — create an organization, a project, three environments and a public + secret key for each, writing `.nekolog-seed.json` (gitignored). **The document holds only key hashes**; the keys themselves are printed once, as `docs/PLANO.md` §6 requires, and `parseSeedDocument` rejects a document carrying a `value` field so that cannot quietly change. `pnpm seed add-key --environment <name>` mints another key for an existing environment — that is both the rotation the plan asks for and the way back when a key is lost, which is why `init` refuses to overwrite an existing file (new ids would orphan every row already in ClickHouse). Keys do not reach Workers KV yet: no namespace exists until step 1.16, and `keyRecordsFor` already produces exactly what a `kvKeyStore` needs. See `internal/seed/README.md`.
- `pnpm --filter @apps/ingest serve` — the ingestion as a plain Node process on :8787, for local work and for the example. It is the same Hono app the Worker serves, with the keys read from `.nekolog-seed.json` instead of Workers KV and **no spool**: in dev a ClickHouse refusal must be loud, not quietly parked in a bucket. It refuses to start without the seed file or without ClickHouse answering, naming which one is missing. `pnpm --filter @examples/express start` then runs the Express example against it; `curl localhost:3100/orders/ord_7f3a91` produces the row. See `examples/express/README.md`.
- `node internal/deploy/src/render-cli.ts --config apps/ingest/wrangler.json --environment dev --out apps/ingest/wrangler.generated.json` then `pnpm --filter @apps/ingest deploy:dry-run -- --config wrangler.generated.json --env dev` — compiles the Worker exactly as a deploy would, with no Cloudflare account. The dry run needs the *rendered* config: wrangler validates bucket names, so a `${SPOOL_BUCKET}` placeholder is rejected before bundling.
- **The access log's `finish` listener is wrapped in `bindContext`, and that is not decoration** (`examples/express/src/middleware.ts`). An event listener does not inherit the `AsyncLocalStorage` store of whoever registered it — it runs under whatever context is active when the event is emitted, which for a backpressured response is the socket's, not the request's. It happens to work without the wrapper in a fast local test, so `middleware.test.ts` emits `finish` from outside the context on purpose; that is the only test that can tell the difference. The same wrapper is why what the route added later with `addContext` still reaches the line written at the end.
- **The three environments share one ClickHouse, so the separation is in the credentials, not the machine** (`deploy/vm/clickhouse/users.xml.tftpl`). There are ten users: `reader`, `ingest` and `jobs` **per environment**, plus one `migrator` and `default`. `nekolog_ingest_prod` cannot touch `nekolog_dev`. `packages/clickhouse/src/grants.test.ts` reads both this template and the dev file and fails if any of those grants widens. Two things cost real time to find and are easy to undo by accident: the image's `/docker-entrypoint-initdb.d` scripts run as `default` **with no password**, so with a password set they fail *silently* and the databases never appear — which is why a separate `clickhouse-init` service applies them as the migrator; and a `users.d` block for `default` must carry `replace="replace"`, or ClickHouse refuses to start with "Cannot specify multiple authentication methods".
- **`wrangler` does not interpolate environment variables in its config file**, so `apps/*/wrangler.json` carries `${KV_NAMESPACE_ID}`-style placeholders and `internal/deploy`'s `render-cli.ts` writes a `wrangler.generated.json` (gitignored) at deploy time. The renderer **deletes the environments it was not asked for**, which is what makes it impossible to publish `prod` with `dev`'s namespace id, and it fails naming every value that is missing or blank. Secrets never go through it: their names live in `deploy/workers/secrets.json` and `wrangler secret bulk` uploads them from a `0600` file the step deletes. `assertNoSecretVars` refuses a config that carries one anyway. **Neither Worker has a `workers.dev` address or a route in wrangler** — the ingestion's hostname is a `cloudflare_workers_custom_domain` in `infra/modules/environment`, and the jobs Worker has no hostname at all (threats E14/E15). `apps/*/src/wrangler.test.ts` feeds the config's own bindings to the Worker's `assertEnv`, so a missing binding or a forgotten secret fails there instead of on the first request.
- **The OpenTofu provider lock files are committed, and CI runs `init -lockfile=readonly`.** `infra/**/.terraform.lock.hcl` pins each provider's hash; a run that would change one fails instead of silently accepting a different build. They were generated by CI, not by hand — there is no `tofu` binary in this environment, so **the only way to check infra changes here is to push and read the `Infra` workflow**. `fmt -check` and `validate` need no credentials and catch schema mistakes; `plan` cannot run until the account exists.
- `pnpm db:generate` / `pnpm db:migrate` — drizzle-kit against `packages/db`. `generate` needs no database and writes the next `migrations/NNNN_*.sql` from the schema; `migrate` applies them to `DATABASE_URL`. The dev stack's Postgres is `postgres://nekolog:nekolog@localhost:5432/nekolog_dev`. See `packages/db/README.md`.
- `pnpm tracking` — print what `internal/tracking` would create on GitHub from `docs/ETAPAS.md` (milestones, labels, one issue per step); `pnpm tracking -- --apply` actually creates it. Dry-run is the default because creating issues is public and cannot be undone in bulk, and the run is idempotent, so a new step in `ETAPAS.md` just needs another run. It never deletes, renames or closes anything. **It does rewrite the body of an open issue whose step drifted from `docs/ETAPAS.md`** — on 2026-11-03 all 53 open issues still said the PR closes them with `Closes #N`, which this repository cannot do. A closed issue is never touched (it is a record), an item ticked by hand survives the rewrite, and a lone tick is not treated as a change, so the next run cannot undo it. Do **not** run `--include-done` to "complete" the record: every M0/M1 step and 2.0 finished without an issue, and the flag would open 28 issues for work that is already merged, with no PR to link — which the README argues is a worse record than none. See `internal/tracking/README.md`.
- `pnpm changeset` — add a changeset for a package/app you just changed; `pnpm changeset:status` shows what's pending relative to `dev`.
- To run a single package's tests/typecheck directly: `cd packages/config && pnpm test` or `pnpm --filter @nekolog-io/config test`.

## Conventions

- **No comments.** This codebase is deliberately comment-free — the maintainer's explicit call, applied across the whole repo on 2026-10-30. Do not add explanatory comments, JSDoc, section banners, or `TODO`/`NOTE` markers to any `.ts`, `.tsx`, `.mjs`, `.js`, `.css`, `.yml`, or `.yaml` file. Put the explanation in a name, a smaller function, the commit message, the PR body, or a doc under `docs/` — not in the source. Two things are **not** comments and stay: compiler/tool directives (`// @ts-check`, `biome-ignore`, `eslint-disable`) and reference data (the `/* #hex */` annotations next to each OKLCH token in `globals.css`, which are the only record of the original palette values). Markdown prose is unaffected.
- **Relative imports carry the `.ts` extension** in everything Node loads directly — `internal/*`, `packages/*` and the Worker apps — because Node 24 runs this code with no bundler and will not resolve an extensionless specifier. (`apps/web` and `apps/docs` are the exception: Next and Astro bundle them, and neither is ever loaded as raw ESM.) TypeScript resolves it either way and vitest resolves it either way, so a package that gets this wrong looks fine until the first `node some/cli.ts` imports it — which is how `packages/adapters` shipped broken until step 1.13. A test that merely imports a module cannot catch this; `internal/seed/tests/cli.integration.test.ts` spawns a real `node` process, which can.
- **Commits:** Conventional Commits in English, scoped by package/app (e.g. `feat(core): add batching transport`, `fix(ingest): reject payloads above 512 KB`), enforced by commitlint (`npm-conventional` types only — `security/`-prefixed branches still commit as `chore(security): ...` or similar, not `security(...)`, since `security` isn't a valid commit type).
- **Branches:** one step from ETAPAS.md = one branch off `dev`, prefixed `feat/`, `fix/`, `chore/`, `docs/`, `ci/`, `test/`, `security/`, `infra/`, or `a11y/`. PRs into `dev` squash-merge; promotion `dev→qa→main` uses merge commits (no squash) so branches don't diverge. **This is enforced live, not just convention:** GitHub rulesets on `main`/`qa`/`dev` block deletion/force-push and require PRs + passing status checks (nobody has bypass, not even the repo owner), and `.github/workflows/branch-rules.yml` rejects PRs into `qa`/`main` from the wrong source branch. The `gh` CLI is set up and authenticated in this environment — prefer it (`gh pr create`, `gh pr checks --watch`, `gh pr merge --squash --delete-branch`) over raw GitHub API calls.
- **A step merges only when:** CI is green, new tests cover the change, a changeset exists if a package/app changed, UI strings exist in all three locales, docs are updated for anything public-facing, and (if labeled `security`) the security checklist was followed.
- **i18n:** landing page, docs, dashboard (in its own repo), emails, and README ship in pt-BR, en (source/fallback), and es. Code, commits, branches, and PRs are English-only. **This is enforced by tests, not just convention:** `apps/web/i18n/messages.test.ts` fails if a message key is missing, stale, or blank in any locale, and `apps/docs/tests/i18n-parity.test.ts` fails if a docs page lacks a translation (or a translation has no English source). Each app's locale list is a single exported constant (`apps/web/i18n/locales.ts`, `apps/docs/locales.mjs`) that both the app config and its test read, so adding a locale immediately makes the test demand translations.
- **Security is the top priority** (docs/PLANO.md §14): parameterized SQL only, permission checks server-side on every route/query, SSRF protections on alert webhooks, CSV export must guard against formula injection, PRs touching `apps/ingest`, `internal/db`, or permission-checking code get the `security` label and a dedicated review pass. **[docs/security/threat-model.md](docs/security/threat-model.md) is the working list** — it maps each threat to its mitigation and marks what's implemented vs. still planned, so when you build a feature, check which threats it's supposed to close. It also records what was accepted *without* full mitigation, so don't "fix" those without reading why. Operational procedures live in [docs/runbooks/](docs/runbooks/README.md) (none exercised yet — the infra doesn't exist).
- **Logs are untrusted input** — anyone with a public key can send arbitrary text. Never render log content with `dangerouslySetInnerHTML`; escape everything.
- **The legal documents are typed data in `apps/web/content/legal/`, one module per locale, and they have not been reviewed by a lawyer.** They are rendered as text — never as HTML — and `content/legal/parity.test.ts` fails when a translation drops a clause, reorders a section, leaves an entry blank, lags behind on the `updated` date, or still carries the English sentence. Changing one locale means changing all three. The text deliberately states what is never stored (the IP address, the password, the key) and names every processor, so **a new sub-processor or a new kind of data collected means editing the privacy policy in three languages** — that is the point of keeping it in the repository. Before the public launch (step 6.8) it still needs a legal review and the controller's full civil identification.
- **The browser SDK puts the key in the URL on exactly one path, and that is not an oversight.** `navigator.sendBeacon` cannot send a header, so the `pagehide` flush posts to `/v1/logs?key=nekolog_pk_…` with a `text/plain` body — `application/json` would ask for a CORS preflight, and a preflight does not happen while the page is unloading (`apps/ingest`'s `ACCEPTED_CONTENT_TYPES` already allows both for this reason). Every other send keeps the key in `Authorization`. A **secret** key handed to `createLogger` is refused and nothing is sent: it would be a published credential, and `publicKeyOnly` has a test for it. The browser's `maxBatchBytes` is capped at 60 KB because that is the beacon's quota, and a refused beacon falls back to `fetch` with `keepalive` rather than losing the batch. `page.url` drops the query string and the fragment by default — reset tokens and invite codes live there. Its tests run against a real DOM (happy-dom) with `ErrorEvent`, `pagehide` and `visibilitychange` actually dispatched; a real browser is step 3.12.
- **Breadcrumbs ride on `error` and `fatal` only, as one 4 KB attribute, and that is forced by the payload contract.** Spec 1 has no breadcrumb field, so the trail travels as a `breadcrumbs` attribute in JSON; attaching 4 KB to each of 500 events would make a 2 MB batch the server refuses outright. `serialiseTrail` trims from the **oldest** end until it fits, never mid-record, so what arrives always parses. A click records `button#pay`, never the element's text or `value` — a label can name a person. Navigation and fetch addresses go through the same `page.url` stripping, the request body and headers are never read, and `ingestMatcher` skips the SDK's own batch so a flush does not become a breadcrumb of the next one. The two monkey-patches (`window.fetch`, `history.pushState`/`replaceState`) call through, return what the original returned, rethrow what it rejected, and restore **only if nobody patched after us**. XHR is deliberately not patched. A breadcrumb's `at` is an **ISO string, never milliseconds**: an epoch-millisecond value is 13 digits and roughly one in ten passes the Luhn check, so core's card filter replaced it with `[redacted]` outside the quotes and the whole trail stopped being JSON — with 20 crumbs that was near-certain, and `breadcrumbs.test.ts` walks 2 000 consecutive milliseconds in both forms to pin it. Note that core's redaction catches cards, CPF, `Bearer …` and nekolog keys but **not e-mail addresses** — that is core's scope, not an oversight here.
- **`traceparent` goes only where it was configured, and the matcher is deliberately strict.** The W3C spec lives in `packages/core/src/trace.ts` (`parseTraceparent`, `traceparentOf`, `traceForRequest`, `childSpan`, `createTraceTargetMatcher`); the browser, Node and `examples/express` all use it instead of three copies. `createTraceTargetMatcher` compares **whole host or whole origin**, never a text prefix — `api.shop.test` does not match `api.shop.test.evil.test`, a different port is a different origin, `http:` is not `https:`, a path entry must match at a segment boundary, and any scheme other than `http`/`https` is refused. The browser defaults to the page's own origin (a `traceId` is an internal identifier, and an extra header on a cross-origin request turns it into a preflight that can fail); the ingestion endpoint is skipped. **Node has no default at all**: `installTracePropagation({targets})` requires the list, because there is no "own origin" on a server and quietly sending internal ids to a payment gateway is not a default anyone wants. Adding the header never breaks the request — `Headers`, pair lists, plain objects and a prepared `Request` are each extended, not replaced, and anything unexpected sends the request *without* the header rather than not sending it. The browser uses **one** fetch patch for both breadcrumbs and the header (`installFetchPatch`), not two.
- **The Nest interceptor opens the context around the *subscription*, and reads the error status from the error.** A Nest interceptor returns an Observable and the controller runs when something subscribes — after `intercept` has returned — so wrapping `next.handle()` in `runWithContext` leaves the handler outside the context; the interceptor returns a new `Observable` and subscribes inside the scope. And Nest's exception filter has **not** set `response.statusCode` when the interceptor is told about a thrown error, so the error path reads `HttpException.getStatus()` or a `status` field instead — reading the response logged a 500 as `info`, which an end-to-end test caught. The package deliberately uses **no decorator syntax**, so it compiles without `experimentalDecorators`/`emitDecoratorMetadata`; a `Module({})(NekologModule)` call was removed after the sabotage harness proved it defines no metadata at all (Nest's `Module` writes one key per property of the object it is given, and `{}` has none).
- **The three server middlewares share one implementation, in `@nekolog-io/node`'s `src/http.ts`.** `startRequest` continues the caller's trace, validates or mints the request id and returns the response headers; `levelForStatus`, `requestIdFrom` and the access line live there too. An incoming `x-request-id` is accepted only as up to 64 characters of `[A-Za-z0-9._:-]` — it goes straight back out in a response header, so trusting it would be letting the client write one. The access line names the **route pattern**, never the address. Three things are easy to undo by accident: Express wraps the `finish` listener in `bindContext` (an event listener does not inherit the registrant's `AsyncLocalStorage`, and the only test that can tell fires `finish` from outside the context on purpose); Hono records in a `finally` so a middleware further down that throws still gets its line, which `app.request()` cannot show because Hono catches handler errors itself — the test calls the middleware directly with a rejecting `next`; and the Fastify plugin carries `Symbol.for('skip-override')` or its hooks would be encapsulated in the `register` scope and log nothing, and it calls `done()` **inside** `runWithContext` so the context reaches the handler. `withErrorLog` logs and calls `next(error)`: the error response is the app's to decide, and our logging failing must not swallow the app's error.
- **`@nekolog-io/next` has two entries and that is load-bearing.** The root entry is server-side and pulls `node:async_hooks` through `@nekolog-io/node`; `@nekolog-io/next/client` is `'use client'` and imports nothing from Node. `register()` builds one logger per process however many times Next calls `instrumentation.ts`, uses the Node logger with process hooks on `nodejs` and a core logger with `runtime: 'edge'` and no hooks on `edge`, and treats an unknown `NEXT_RUNTIME` as `nodejs` rather than believing it. `onRequestError` records the path without its query, the method and the Next routing fields, and **never the headers** — session cookie, `Authorization` — and never throws back into Next when our own logger fails. Its `attw` runs with `--profile node16` because node10 cannot resolve a subpath export and Next needs Node 18 anyway.
- **The React provider does not own the client, the page does.** 
ekologClient() is a module-level singleton, so two nested NekologProviders, StrictMode's double render and a route that unmounts and remounts all share one client with the global handlers installed once — and unmounting the provider closes nothing, because the page is still the page. closeClient() exists for tests and for an app that really is ending. `useLogger` outside a provider returns a console-backed logger and warns once instead of throwing: React's convention is to throw, but this SDK must never throw into the host app, and a forgotten provider cannot be why a production page goes blank. The boundary's `onError` runs in a `finally`, so a logger that throws cannot take the app's own handler down with it.
- **The offline queue parks only a transport failure, and never writes the key.** `parkingSender` catches a rejected `fetch` — what "no network" looks like — and puts the batch in IndexedDB; a `400` is a refusal the server will repeat, so it passes through and the batch is dropped rather than retried forever. On replay, `429`/`5xx` keep a batch and `4xx` deletes it. The stored record is `{at, url, body}` only: the `Authorization` header is rebuilt from the live key, because a key in a browser database is a credential at rest for nothing, and a test asserts the record has no other field. At most 50 batches, 2 MB and 7 days, oldest out first. If IndexedDB refuses, the **original** error is rethrown instead of a fake 202 — and `within()` awaits the transaction's completion for the same reason: an `add` that succeeded inside a transaction that then aborted (quota) is not a saved batch. `installOnlineReplay` runs once at install, which is what makes the error that happened offline arrive on the next visit.
- **`lint` depends on the package's own `build`, not just `^build`.** Each published package's `lint` script runs `pnpm run build && pnpm pack`, and tsdown cleans `dist/` first; with `dependsOn: ["^build"]` Turbo could run `pkg#build` and `pkg#lint` at the same time and the pack would find an empty `dist/`, which is exactly how `@nekolog-io/clickhouse` failed CI once the browser package changed the scheduling. Don't relax it back.
- **The security headers come from `internal/security-headers`, and `script-src` has no opt-out.** `apps/web` builds a nonce per response in `proxy.ts` (Next 16 renamed `middleware.ts` to `proxy.ts`; the exported function must be called `proxy`), and `apps/docs` — static, so no per-request nonce exists — carries a hash per inline script in a **generated** `apps/docs/vercel.json`. Its `build` fails when that file stops covering what the build produced; regenerate with `pnpm --filter @apps/docs headers:write`. Two things are easy to undo by accident: the docs' `style-src 'unsafe-inline'` is there because Starlight writes hundreds of `style="…"` attributes, which no hash or nonce reaches, and the generator **refuses** to emit a policy when a `<style>` element appears, because a hash there makes the browser ignore `'unsafe-inline'` and breaks all of them silently. `apps/web` writes no style attribute and a test fails if one appears. CI now runs **Build before Test**, because `WEB_HEADERS_TEST_REQUIRED` and `DOCS_HEADERS_TEST_REQUIRED` turn a missing build into a failure instead of a skip.

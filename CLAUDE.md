## What NekoLog is

An open-core logging platform for JS/TS apps (frontend + backend): npm SDKs that batch-send logs, an ingestion API, ClickHouse for storage, background jobs for alerts, and a dashboard with search/filters/charts/alerts, with separate API keys per environment (`nekolog_pk_…` public, `nekolog_sk_…` secret — the key determines the environment, SDKs never pass one explicitly).

It's a personal/portfolio project designed to run entirely on free-tier cloud services (Cloudflare Workers/KV/R2/Tunnel, Oracle Always Free VM for ClickHouse, Neon Postgres, Upstash Redis, Vercel, Resend). The SDKs, ingestion, jobs, and public read API are self-hostable via a single `docker-compose`; **the dashboard is not** — it's closed-source and cloud-only (see "Two repositories" above). The only paid cost is the `nekolog.io` domain.

### Architecture at a glance

```
SDKs (browser / node) → HTTPS batch (gzip)
   → Cloudflare Worker "ingest" (Hono) → KV (key→project/env/quota) → ClickHouse (via Tunnel, on Oracle VM)
   Cloudflare Worker "jobs" (cron, 1 min) → alerts/issues/usage/quotas → Resend/Slack/Discord/webhook
   Vercel: Next.js dashboard (closed-source, deployed from the separate nekolog-dashboard repo)
      → Neon Postgres (users/orgs/projects/keys/alerts), Upstash Redis (auth), Resend
   Cloudflare R2: source maps
```

Key invariants from `docs/PLANO.md` §3–4 that should guide any implementation:

- **Ingestion does no I/O beyond the write; processing happens elsewhere.** The ingest API validates, derives what comes out of the event itself, and writes. Anything needing a network call or a database read — source-map resolution, alert evaluation, issue building — runs in `apps/jobs`. **Fingerprinting is computed at ingestion** (spec 5, step 4.5): it is pure CPU over the event in hand, and ClickHouse cannot backfill the `fingerprint` column after the insert without a mutation. `docs/PLANO.md` §3 principle 1 states the rule in this form; an older wording said error grouping ran outside ingestion, which contradicted spec 5 and `ETAPAS.md` 4.5 and was settled in favour of ingestion on 2026-10-31.
- **Ingestion never depends on Postgres or Redis** — keys live in Workers KV so Neon's cold-start/hibernation never adds latency to the hot path.
- **Vendor-specific behavior is always behind an interface** (`KeyStore`, `RateLimiter`, `BlobStore`, `Mailer`, `LogStore`, `RedisClient` in `internal/adapters/`) so the same code runs on free-tier cloud and in self-host (Redis/Valkey, Garage, SMTP, local ClickHouse/Postgres).
- **The SDK must never throw into the host app** and ships with zero dependencies.
- Uses OpenTelemetry-style log shape and W3C `traceparent` propagation.
- **Privacy-by-default (LGPD):** sensitive fields are stripped client- and server-side; raw IPs are never stored, only resolved country.

## Commands that work today

- `pnpm install` — install everything (pnpm 12 via Corepack; `minimumReleaseAge` in `pnpm-workspace.yaml` will refuse packages published too recently — this is intentional, not a bug).
- `pnpm dev` — starts the dev `docker-compose` stack (ClickHouse on :8123, Postgres on :5432, Valkey on :6379, Mailpit on :8025 web UI, Garage S3 on :3900 and its admin API on :3903) and then `turbo run dev`, which also starts `apps/web` on :3000 (Turbopack) and `apps/docs` on :4321/docs (Astro). Copy `.env.example` to `.env` first. `pnpm dev:infra:down` / `pnpm dev:infra:logs` manage the docker stack directly. **Verified working end to end on 2026-10-30**, including an S3 round trip against Garage. Garage replaced MinIO, which withdrew its public images — see ADR [0013](docs/adr/0013-garage-no-lugar-do-minio.md); its credentials have a strict format (`GK` + 24 hex, secret of exactly 64 hex) that `deploy/garage-init.sh` checks and explains.
- `pnpm lint` / `pnpm typecheck` / `pnpm test` / `pnpm build` — Turborepo tasks fanning out to every package's own script (currently `apps/web`, `apps/docs`, `internal/config`, `internal/schema`, `internal/adapters` define some). A package with no matching script is silently skipped by Turbo — that's expected, not a failure. `apps/docs` deliberately has **no** `typecheck` script: `astro check` doesn't support TypeScript 7 and Astro is deprecating it — `astro build` validates the content schemas instead (see `apps/docs/README.md`).
- `apps/web` (landing page) locale: resolved from a `NEKOLOG_LOCALE` cookie, falling back to `Accept-Language`, falling back to `en` (see `apps/web/i18n/request.ts`) — no `/[locale]/` URL prefix. This mirrors the approach the dashboard repo should use too, since `docs/PLANO.md` §10.1's route map never puts locale in the path. The in-page `LocaleSwitcher`/`ThemeToggle` components are temporary proof-of-wiring from step 0.11, not final landing-page UI.
- `pnpm ch:status` / `pnpm ch:migrate` / `pnpm ch:new <name>` — the ClickHouse migration runner in `internal/clickhouse` (spec 3). Forward-only, one SQL command per file in `internal/clickhouse/migrations/`, checksummed in a `_migrations` table; it halts on an edited migration, a gap in the numbering, an out-of-order apply, or a migration the database remembers but the repo no longer has. It never creates the database. The CLI runs `.ts` directly on Node 24 — no build. Its integration tests hit the real ClickHouse on :8123 and are skipped (with a stderr notice) when nothing answers; CI sets `CLICKHOUSE_TEST_REQUIRED=1` so a skip there is a failure instead. See `internal/clickhouse/README.md`.
- The dev ClickHouse has **four users with separate grants** (`deploy/clickhouse-users.dev.xml`, mounted into `users.d/` so it applies on restart without wiping the volume): `nekolog_reader`, `nekolog_ingest`, `nekolog_jobs`, `nekolog_migrator`. Note that `nekolog_ingest` is *not* INSERT-only — ClickHouse requires `SELECT` on the columns a materialized view reads, and without it the INSERT lands in `logs`, fails to feed the view, and returns an error. It therefore holds column-scoped `SELECT` on the six columns the two views read (`project_id`, `environment_id`, `timestamp`, `received_at`, `level`, `service`), and nothing more (see `docs/PLANO.md` §7 and threats E10/E11). **Adding a materialized view means widening that grant before the migration runs** — in dev the mounted file hot-reloads without a restart, but anywhere else the order is the deployer's job.
- **There are two rollups and they answer different questions.** `logs_per_minute` groups by the client-supplied `timestamp` and feeds the charts; `usage_per_minute` groups by the server-stamped `received_at` and feeds usage and quota. Quota must never be computed from `logs_per_minute`: a sender could backdate its events and never appear in today's count (threat T7). `apps/jobs/tests/quota.integration.test.ts` pins this with a real 2020-dated event.
- **Published packages build with `tsdown` and must set `isolatedDeclarations: true`** (see `packages/core/tsconfig.json`). TypeScript 7 no longer exposes the classic API that tsdown's `.d.ts` generator used, so declarations are emitted by Oxc instead — which requires explicit type annotations on exported values whose type can't be inferred syntactically (`export const MAX_MESSAGE_BYTES: number = 16 * 1024`). Don't "fix" those annotations by removing them. Each package's `lint` script runs `publint` and `@arethetypeswrong/cli` against the built output.
- **`@nekolog-io/core` has zero runtime dependencies by contract**, so it cannot import `@internal/schema` (which pulls in Valibot). The payload limits are deliberately duplicated in `packages/core/src/limits.ts`; `packages/core/src/contract.test.ts` compares them one by one against `@internal/schema` and runs the logger's own events through the real ingestion parser, so the duplication cannot drift silently. Keep that test passing rather than deleting the duplication.
- **A package that depends on another workspace package resolves it through its built `dist/`**, not its source. Turbo's `typecheck`/`test`/`lint` all `dependsOn: ["^build"]`, so CI is fine — but locally, after changing `packages/core`, run `pnpm --filter @nekolog-io/core build` before typechecking `packages/node`, or you'll see stale types.
- **`internal/clickhouse` has three entry points** — the root (which pulls `node:fs` through the migration runner), `/client`, and `/log-store`. A Worker must import one of the subpaths, not the root. Don't collapse them back into one entry to "simplify".
- **The ClickHouse inserts set `input_format_skip_unknown_fields=0`** (`internal/clickhouse/src/log-store.ts`). Without it ClickHouse accepts a row carrying a column the table does not have, writes the rest with defaults and answers success — silent data loss on any schema drift. The price is that a migration must be applied before code that writes a new column, which the forward-only runner already implies.
- **`@nekolog-io/node`'s process hooks are tested against real spawned Node processes** (`packages/node/tests/`), not just a fake `process`, because the failure mode being guarded against (a listener that stops Node from crashing, turning a dead service into a zombie) only shows up in a real process. The fixtures are run directly as `.ts` by Node 24's type stripping, so they need no build. One test is skipped on Windows with a stderr notice — `process.kill(pid, 'SIGTERM')` terminates the process there instead of delivering the signal to a listener; CI runs on Linux, where it does run.
- **The ClickHouse deduplication token is `<environmentId>:<batchId>`, not the bare `batchId`** (`internal/spool/src/envelope.ts`). `batchId` is chosen by the client and ClickHouse deduplicates per table partition, which every project shares — an unscoped token lets one tenant's batch silently suppress another's. Don't "simplify" it back.
- **The rate limit and the attribute budget are per-isolate, by design, and the docs say so.** A Cloudflare Worker runs many isolates, so the in-memory limiter's real ceiling is the configured one times the instance count — it is a burst brake, not a volume control. The daily quota in KV is the actual cap. Don't "fix" either by claiming a guarantee they can't make.
- **The quota task must never treat "I can't measure" as "nobody is over".** If the ClickHouse usage query fails, `quota-block` returns without touching KV; computing an empty block list there would unblock every tenant during an outage. There's a test for it.
- **`quota-block` writes KV only when the set of blocked environments changes**, and keeps every block in one `quota:blocks` document. The free tier allows 1,000 writes and 1,000 list operations per day while the cron wakes 1,440 times, so per-environment keys or an unconditional write would exhaust the quota on their own.
- **`apps/jobs` decides cadence from the cron's `scheduledTime`, never from remembered state** (`(minute - offsetMinutes) % everyMinutes === 0`). A Worker isolate does not survive between runs, so a "last run" variable would work locally and misfire in production. The jobs app also exposes **no route that runs a task** — only `GET /health` — and `apps/jobs/src/app.test.ts` fails if one is added (threat E12). Don't add a `/run` endpoint for convenience.
- `pnpm check` — `biome check --write .` (formats + lints; excludes `**/*.md` and lockfiles — see `biome.json`). CI instead runs `biome ci .` (no writes).
- `pnpm seed init` — create an organization, a project, three environments and a public + secret key for each, writing `.nekolog-seed.json` (gitignored). **The document holds only key hashes**; the keys themselves are printed once, as `docs/PLANO.md` §6 requires, and `parseSeedDocument` rejects a document carrying a `value` field so that cannot quietly change. `pnpm seed add-key --environment <name>` mints another key for an existing environment — that is both the rotation the plan asks for and the way back when a key is lost, which is why `init` refuses to overwrite an existing file (new ids would orphan every row already in ClickHouse). Keys do not reach Workers KV yet: no namespace exists until step 1.16, and `keyRecordsFor` already produces exactly what a `kvKeyStore` needs. See `internal/seed/README.md`.
- `pnpm tracking` — print what `internal/tracking` would create on GitHub from `docs/ETAPAS.md` (milestones, labels, one issue per step); `pnpm tracking -- --apply` actually creates it. Dry-run is the default because creating issues is public and cannot be undone in bulk, and the run is idempotent, so a new step in `ETAPAS.md` just needs another run. It never deletes, renames or closes anything. See `internal/tracking/README.md`.
- `pnpm changeset` — add a changeset for a package/app you just changed; `pnpm changeset:status` shows what's pending relative to `dev`.
- To run a single package's tests/typecheck directly: `cd internal/config && pnpm test` or `pnpm --filter @internal/config test`.

## Conventions

- **No comments.** This codebase is deliberately comment-free — the maintainer's explicit call, applied across the whole repo on 2026-10-30. Do not add explanatory comments, JSDoc, section banners, or `TODO`/`NOTE` markers to any `.ts`, `.tsx`, `.mjs`, `.js`, `.css`, `.yml`, or `.yaml` file. Put the explanation in a name, a smaller function, the commit message, the PR body, or a doc under `docs/` — not in the source. Two things are **not** comments and stay: compiler/tool directives (`// @ts-check`, `biome-ignore`, `eslint-disable`) and reference data (the `/* #hex */` annotations next to each OKLCH token in `globals.css`, which are the only record of the original palette values). Markdown prose is unaffected.
- **Relative imports carry the `.ts` extension**, everywhere, because Node 24 runs this code with no bundler and will not resolve an extensionless specifier. TypeScript resolves it either way and vitest resolves it either way, so a package that gets this wrong looks fine until the first `node some/cli.ts` imports it — which is how `internal/adapters` shipped broken until step 1.13. A test that merely imports a module cannot catch this; `internal/seed/tests/cli.integration.test.ts` spawns a real `node` process, which can.
- **Commits:** Conventional Commits in English, scoped by package/app (e.g. `feat(core): add batching transport`, `fix(ingest): reject payloads above 512 KB`), enforced by commitlint (`npm-conventional` types only — `security/`-prefixed branches still commit as `chore(security): ...` or similar, not `security(...)`, since `security` isn't a valid commit type).
- **Branches:** one step from ETAPAS.md = one branch off `dev`, prefixed `feat/`, `fix/`, `chore/`, `docs/`, `ci/`, `test/`, `security/`, `infra/`, or `a11y/`. PRs into `dev` squash-merge; promotion `dev→qa→main` uses merge commits (no squash) so branches don't diverge. **This is enforced live, not just convention:** GitHub rulesets on `main`/`qa`/`dev` block deletion/force-push and require PRs + passing status checks (nobody has bypass, not even the repo owner), and `.github/workflows/branch-rules.yml` rejects PRs into `qa`/`main` from the wrong source branch. The `gh` CLI is set up and authenticated in this environment — prefer it (`gh pr create`, `gh pr checks --watch`, `gh pr merge --squash --delete-branch`) over raw GitHub API calls.
- **A step merges only when:** CI is green, new tests cover the change, a changeset exists if a package/app changed, UI strings exist in all three locales, docs are updated for anything public-facing, and (if labeled `security`) the security checklist was followed.
- **i18n:** landing page, docs, dashboard (in its own repo), emails, and README ship in pt-BR, en (source/fallback), and es. Code, commits, branches, and PRs are English-only. **This is enforced by tests, not just convention:** `apps/web/i18n/messages.test.ts` fails if a message key is missing, stale, or blank in any locale, and `apps/docs/tests/i18n-parity.test.ts` fails if a docs page lacks a translation (or a translation has no English source). Each app's locale list is a single exported constant (`apps/web/i18n/locales.ts`, `apps/docs/locales.mjs`) that both the app config and its test read, so adding a locale immediately makes the test demand translations.
- **Security is the top priority** (docs/PLANO.md §14): parameterized SQL only, permission checks server-side on every route/query, SSRF protections on alert webhooks, CSV export must guard against formula injection, PRs touching `apps/ingest`, `internal/db`, or permission-checking code get the `security` label and a dedicated review pass. **[docs/security/threat-model.md](docs/security/threat-model.md) is the working list** — it maps each threat to its mitigation and marks what's implemented vs. still planned, so when you build a feature, check which threats it's supposed to close. It also records what was accepted *without* full mitigation, so don't "fix" those without reading why. Operational procedures live in [docs/runbooks/](docs/runbooks/README.md) (none exercised yet — the infra doesn't exist).
- **Logs are untrusted input** — anyone with a public key can send arbitrary text. Never render log content with `dangerouslySetInnerHTML`; escape everything.

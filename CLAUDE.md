## What NekoLog is

An open-core logging platform for JS/TS apps (frontend + backend): npm SDKs that batch-send logs, an ingestion API, ClickHouse for storage, background jobs for alerts, and a dashboard with search/filters/charts/alerts, with separate API keys per environment (`nekolog_pk_…` public, `nekolog_sk_…` secret — the key determines the environment, SDKs never pass one explicitly).

**Everything runs on one VPS, as of item D4 on 2026-11-05.** Until then it was designed for free-tier cloud (Cloudflare Workers/KV/R2/Tunnel, Oracle Always Free VM, Neon, Upstash, Vercel); all of that infrastructure code was deleted, having never been applied once. What is left of Cloudflare is the free plan in front of the machine — DNS and proxy — plus one R2 bucket for backups. `docs/COMERCIAL.md` holds the decisions; `docs/PLANO.md` still describes the old platform and its rewrite is item **D5**.

### Architecture at a glance

```
SDKs (browser / node) → HTTPS batch (gzip)
   → Cloudflare Free (DNS + proxy) → Caddy on the VPS → ingest container (Hono on Node)
      → file KV (key→project/env/quota) → ClickHouse container
   jobs container (an in-process scheduler, 1 min) → alerts/issues/usage/quotas → Resend/Discord/webhook
   api container: the public read API; web and docs containers behind the same Caddy
   the dashboard (closed-source, from the separate nekolog-dashboard repo) is item B7
   Cloudflare R2: source maps
```

Key invariants from `docs/PLANO.md` §3–4 that should guide any implementation:

- **Ingestion does no I/O beyond the write; processing happens elsewhere.** The ingest API validates, derives what comes out of the event itself, and writes. Anything needing a network call or a database read — source-map resolution, alert evaluation, issue building — runs in `apps/jobs`. **Fingerprinting is computed at ingestion** (spec 5, step 4.5): it is pure CPU over the event in hand, and ClickHouse cannot backfill the `fingerprint` column after the insert without a mutation. `docs/PLANO.md` §3 principle 1 states the rule in this form; an older wording said error grouping ran outside ingestion, which contradicted spec 5 and `ETAPAS.md` 4.5 and was settled in favour of ingestion on 2026-10-31.
- **Ingestion never depends on Postgres or Redis** — keys live in Workers KV so Neon's cold-start/hibernation never adds latency to the hot path.
- **Vendor-specific behavior is always behind an interface** (`KeyStore`, `RateLimiter`, `BlobStore`, `Mailer`, `LogStore`, `RedisClient` in `packages/adapters/`) so the same code runs on free-tier cloud and in self-host (Redis/Valkey, Garage, SMTP, local ClickHouse/Postgres).
- **The SDK must never throw into the host app** and ships with zero dependencies.
- Uses OpenTelemetry-style log shape and W3C `traceparent` propagation.
- **Privacy-by-default (LGPD):** sensitive fields are stripped client- and server-side; raw IPs are never stored, only resolved country.

Copy `.env.example` to `.env` first. `pnpm dev:infra:down` / `pnpm dev:infra:logs` manage the docker stack directly. **Verified working end to end on 2026-10-30**, including an S3 round trip against Garage. Garage replaced MinIO, which withdrew its public images — see ADR [0013](docs/adr/0013-garage-no-lugar-do-minio.md); its credentials have a strict format (`GK` + 24 hex, secret of exactly 64 hex) that `deploy/garage-init.sh` checks and explains.
- `pnpm lint` / `pnpm typecheck` / `pnpm test` / `pnpm build` — Turborepo tasks fanning out to every package's own script (currently `apps/web`, `apps/docs`, `packages/config`, `internal/schema`, `packages/adapters` define some). A package with no matching script is silently skipped by Turbo — that's expected, not a failure. `apps/docs` deliberately has **no** `typecheck` script: `astro check` doesn't support TypeScript 7 and Astro is deprecating it — `astro build` validates the content schemas instead (see `apps/docs/README.md`).
- `apps/web` (landing page) locale: resolved from a `NEKOLOG_LOCALE` cookie, falling back to `Accept-Language`, falling back to `en` (see `apps/web/i18n/request.ts`) — no `/[locale]/` URL prefix. This mirrors the approach the dashboard repo should use too, since `docs/PLANO.md` §10.1's route map never puts locale in the path. `LocaleSwitcher` and `ThemeToggle` now sit in `components/site-header.tsx`; every outgoing link goes through `lib/links.ts`, which is also what resolves a docs URL into the reader's own locale.
- `pnpm ch:status` / `pnpm ch:migrate` / `pnpm ch:new <name>` — the ClickHouse migration runner in `packages/clickhouse` (spec 3). Forward-only, one SQL command per file in `packages/clickhouse/migrations/`, checksummed in a `_migrations` table; it halts on an edited migration, a gap in the numbering, an out-of-order apply, or a migration the database remembers but the repo no longer has. It never creates the database. The CLI runs `.ts` directly on Node 24 — no build. Its integration tests hit the real ClickHouse on :8123 and are skipped (with a stderr notice) when nothing answers; CI sets `CLICKHOUSE_TEST_REQUIRED=1` so a skip there is a failure instead. See `packages/clickhouse/README.md`.
- The dev ClickHouse has **four users with separate grants** (`deploy/clickhouse-users.dev.xml`, mounted into `users.d/` so it applies on restart without wiping the volume): `nekolog_reader`, `nekolog_ingest`, `nekolog_jobs`, `nekolog_migrator`. Note that `nekolog_ingest` is *not* INSERT-only — ClickHouse requires `SELECT` on the columns a materialized view reads, and without it the INSERT lands in `logs`, fails to feed the view, and returns an error. It therefore holds column-scoped `SELECT` on the six columns the two views read (`project_id`, `environment_id`, `timestamp`, `received_at`, `level`, `service`), and nothing more (see `docs/PLANO.md` §7 and threats E10/E11). **Adding a materialized view means widening that grant before the migration runs** — in dev the mounted file hot-reloads without a restart, but anywhere else the order is the deployer's job.
- **There are two rollups and they answer different questions.** `logs_per_minute` groups by the client-supplied `timestamp` and feeds the charts; `usage_per_minute` groups by the server-stamped `received_at` and feeds usage and quota. Quota must never be computed from `logs_per_minute`: a sender could backdate its events and never appear in today's count (threat T7). `apps/jobs/tests/quota.integration.test.ts` pins this with a real 2020-dated event.
- **Published packages build with `tsdown` and must set `isolatedDeclarations: true`** (see `packages/core/tsconfig.json`). TypeScript 7 no longer exposes the classic API that tsdown's `.d.ts` generator used, so declarations are emitted by Oxc instead — which requires explicit type annotations on exported values whose type can't be inferred syntactically (`export const MAX_MESSAGE_BYTES: number = 16 * 1024`). Don't "fix" those annotations by removing them. Each package's `lint` script runs `publint` and `@arethetypeswrong/cli` against the built output.
- **`@nekolog-io/core` has zero runtime dependencies by contract**, so it cannot import `@internal/schema` (which pulls in Valibot). The payload limits are deliberately duplicated in `packages/core/src/limits.ts`; `packages/core/src/contract.test.ts` compares them one by one against `@internal/schema` and runs the logger's own events through the real ingestion parser, so the duplication cannot drift silently. Keep that test passing rather than deleting the duplication.
- **There are two kinds of published package here, and they resolve differently in the workspace.** The SDKs (`core`, `node`) point `exports` straight at `dist/`: a workspace dependent resolves them through the built output, not the source, so after changing `packages/core` run `pnpm --filter @nekolog-io/core build` before typechecking `packages/node` or you'll see stale types (Turbo's `typecheck`/`test`/`lint` all `dependsOn: ["^build"]`, so CI is fine). The shared internals (`adapters`, `clickhouse`, `config`) instead keep `exports` on `./src/*.ts` and declare the `dist/` mapping under **`publishConfig`**, which `pnpm pack` applies at publish time. That is deliberate: these are run from source inside this repo — `pnpm ch:migrate`, `pnpm seed` and `pnpm --filter @apps/ingest serve` all load them as `.ts` with no build step, and pointing `exports` at `dist/` would quietly break that. The cost is that `publint`/`attw` must inspect the **packed tarball** rather than the directory, which is why each `lint` script runs `pnpm pack --out package.tgz` first. Don't "simplify" either pattern into the other without reading this.
- **`@nekolog-io/db` publishes its TypeScript source as its types, and that is not an oversight.** `pgTable(...)` returns a `PgTableWithColumns<…>` nobody writes by hand, so `isolatedDeclarations` — which TypeScript 7 forces on anything with generated declarations — is not an option. `publishConfig.types` points at `./src/index.ts` and the source ships in the tarball. The consequence is a rule: **the published `src/index.ts` imports no sibling file**, because the consumer compiles it with its own `tsconfig` and a `./tables.ts` import would need their `allowImportingTsExtensions`. `internal/release/src/packaging.test.ts` fails if a relative import appears there.
- **Every outgoing e-mail is checked before the network call, and the allowlist fails closed.** `assertMessage` refuses a `\r`, `\n` or null byte in the recipient or subject — that is how an unseen `bcc:` is forged — and demands a single lowercased address, so display names, commas and angle brackets are out. Both `resendMailer` and `smtpMailer` run it *before* dispatching, with a test proving nothing reached `fetch` or the transport. `allowlistedMailer` enforces `EMAIL_ALLOWLIST` in dev and qa and **an empty list allows nobody**: a missing variable is a fresh machine, not permission to write to strangers. Entries match an address exactly or a domain through a leading `@`, so a `+tag` or a lookalike domain does not slip through.
- **The Redis adapters take no dependency on a vendor and run Lua by hash.** `upstashRedis({url, token})` needs only `fetch`; `nodeRedis(client)` takes an ioredis-shaped object the caller injects, the way `kvKeyStore` takes a KV binding — so `@nekolog-io/adapters` still has zero runtime dependencies and still bundles into a Worker. Both cache the SHA from `SCRIPT LOAD` and call `EVALSHA`, falling back to the text only on `NOSCRIPT`; Upstash's free tier counts commands and the OTP script is dozens of lines. An error that is not `NOSCRIPT` is rethrown, so a replica's `READONLY` cannot be mistaken for a missing script. `prefixedRedis` namespaces the `KEYS` of an `eval` but **not** its `ARGV` — an argument is data, not an address — and there is a test for each half.
- **`pnpm-workspace.yaml` overrides `esbuild@<0.25.0` and that is a security fix, not tidying.** `drizzle-kit` reaches the deprecated `@esbuild-kit/*` loaders, which pin esbuild 0.18.20 — vulnerable to GHSA-67mh-4wv8-2f99. The `dependency-review` workflow failed the PR on it, which is the gate working; **that gate is `pnpm audit` in the `Supply chain` workflow now** — `dependency-review` was removed on 2026-11-06. The override forces a patched esbuild, drizzle-kit still reads the TypeScript schema, and `packages/db`'s tests (which shell out to it) prove it. Don't drop the override without checking that advisory again.
- **The database rules live in the schema, not only in the code that writes to it.** Two repositories write to this Postgres, so `packages/db` carries check constraints — id prefixes, lowercase e-mail, SHA-256-shaped key hashes, a public key that may only write, an invite that cannot grant ownership, a country instead of an address in the audit log. Deleting an organization cascades to projects, environments and keys; deleting a user only nulls `audit_log.actor_user_id`. `packages/db/src/schema.integration.test.ts` applies **the shipped `.sql`** to a throwaway database and tries to violate each rule, so it tests the file that runs rather than the Drizzle object. `migrations.test.ts` regenerates with drizzle-kit and fails if the schema changed without `pnpm db:generate` — without it, editing `src/index.ts` alone changes nothing that runs.
- **The shared internals are ESM-only** (`format: ['esm']`, `attw --profile esm-only`). Their consumers are Node 24, Workers and Next — all ESM — and the migration runner uses `import.meta.url` to find `migrations/`, which has no honest CJS equivalent. The `esm-only` profile is what makes `attw`'s "a require call resolved to an ESM file" warning an expected result instead of a failure.
- **`packages/clickhouse` has three entry points** — the root (which pulls `node:fs` through the migration runner), `/client`, and `/log-store`. A Worker must import one of the subpaths, not the root. Don't collapse them back into one entry to "simplify".
- **The ClickHouse inserts set `input_format_skip_unknown_fields=0`** (`packages/clickhouse/src/log-store.ts`). Without it ClickHouse accepts a row carrying a column the table does not have, writes the rest with defaults and answers success — silent data loss on any schema drift. The price is that a migration must be applied before code that writes a new column, which the forward-only runner already implies.
- **`@nekolog-io/node`'s process hooks are tested against real spawned Node processes** (`packages/node/tests/`), not just a fake `process`, because the failure mode being guarded against (a listener that stops Node from crashing, turning a dead service into a zombie) only shows up in a real process. The fixtures are run directly as `.ts` by Node 24's type stripping, so they need no build. One test is skipped on Windows with a stderr notice — `process.kill(pid, 'SIGTERM')` terminates the process there instead of delivering the signal to a listener; CI runs on Linux, where it does run.
- **The ClickHouse deduplication token is `<environmentId>:<batchId>`, not the bare `batchId`** (`internal/spool/src/envelope.ts`). `batchId` is chosen by the client and ClickHouse deduplicates per table partition, which every project shares — an unscoped token lets one tenant's batch silently suppress another's. Don't "simplify" it back.
- **The rate limit and the attribute budget are per-isolate, by design, and the docs say so.** A Cloudflare Worker runs many isolates, so the in-memory limiter's real ceiling is the configured one times the instance count — it is a burst brake, not a volume control. The daily quota in KV is the actual cap. Don't "fix" either by claiming a guarantee they can't make.
- **The quota task must never treat "I can't measure" as "nobody is over".** If the ClickHouse usage query fails, `quota-block` returns without touching KV; computing an empty block list there would unblock every tenant during an outage. There's a test for it.
- **`quota-block` writes KV only when the set of blocked environments changes**, and keeps every block in one `quota:blocks` document. The free tier allows 1,000 writes and 1,000 list operations per day while the cron wakes 1,440 times, so per-environment keys or an unconditional write would exhaust the quota on their own.
- **`apps/jobs` decides cadence from the cron's `scheduledTime`, never from remembered state** (`(minute - offsetMinutes) % everyMinutes === 0`). A Worker isolate does not survive between runs, so a "last run" variable would work locally and misfire in production. The jobs app also exposes **no route that runs a task** — only `GET /health` — and `apps/jobs/src/app.test.ts` fails if one is added (threat E12). Don't add a `/run` endpoint for convenience.
- `pnpm check` — `biome check --write .` (formats + lints; excludes `**/*.md` and lockfiles — see `biome.json`). CI instead runs `biome ci .` (no writes).
- `pnpm seed init` — create an organization, a project, three environments and a public + secret key for each, writing `.nekolog-seed.json` (gitignored). **The document holds only key hashes**; the keys themselves are printed once, as `docs/PLANO.md` §6 requires, and `parseSeedDocument` rejects a document carrying a `value` field so that cannot quietly change. `pnpm seed add-key --environment <name>` mints another key for an existing environment — that is both the rotation the plan asks for and the way back when a key is lost, which is why `init` refuses to overwrite an existing file (new ids would orphan every row already in ClickHouse). Keys do not reach Workers KV yet: no namespace exists until step 1.16, and `keyRecordsFor` already produces exactly what a `kvKeyStore` needs. See `internal/seed/README.md`.
- `pnpm --filter @apps/ingest serve` — the ingestion as a plain Node process on :8787, for local work and for the example. It is the same Hono app the Worker serves, with the keys read from `.nekolog-seed.json` instead of Workers KV and **no spool**: in dev a ClickHouse refusal must be loud, not quietly parked in a bucket. It refuses to start without the seed file or without ClickHouse answering, naming which one is missing. `pnpm --filter @examples/express start` then runs the Express example against it; `curl localhost:3100/orders/ord_7f3a91` produces the row. See `examples/express/README.md`.
- **The access log's `finish` listener is wrapped in `bindContext`, and that is not decoration** (`examples/express/src/middleware.ts`). An event listener does not inherit the `AsyncLocalStorage` store of whoever registered it — it runs under whatever context is active when the event is emitted, which for a backpressured response is the socket's, not the request's. It happens to work without the wrapper in a fast local test, so `middleware.test.ts` emits `finish` from outside the context on purpose; that is the only test that can tell the difference. The same wrapper is why what the route added later with `addContext` still reaches the line written at the end.
- **The ClickHouse credentials are one per role, in two files, and `grants.test.ts` reads both.** `deploy/clickhouse-users.dev.xml` and `deploy/self-host/clickhouse-users.xml` carry `reader`, `ingest`, `jobs`, `backup` and `migrator`; the test fails if any grant widens, if anyone but the migrator gets DDL, if the ingestion gets a table-wide `SELECT`, or if a literal `<password>` appears instead of `from_env`. Two things cost real time to find and are easy to undo by accident: the image's `/docker-entrypoint-initdb.d` scripts run as `default` **with no password**, so with a password set they fail *silently* and the databases never appear — which is why a separate `clickhouse-init` service applies them as the migrator; and a `users.d` block for `default` must carry `replace="replace"`, or ClickHouse refuses to start with "Cannot specify multiple authentication methods".
- **The infrastructure that is left declares two things, and a test ties both to the code.** `infra/vps` publishes one A record per name the self-host Caddyfile answers on — `internal/infra/src/vps.test.ts` fails in either direction, because a name with no record is unreachable and a record with no Caddy block is a certificate Let's Encrypt can never issue — and one R2 bucket for backups whose lifecycle rule expires **only** the `clickhouse/` prefix. That prefix is compared against `BACKUP_KEY_PREFIX` in the test: the Postgres backup deletes its own old files by `BACKUP_KEEP_DAYS`, so a bucket-wide rule would be a second retention on the same objects with a different number. The same test asserts that every root directory under `infra/` is validated, planned and applied by `.github/workflows/infra.yml`, in both directions.
- **The OpenTofu provider lock files are committed, and CI runs `init -lockfile=readonly`.** `infra/**/.terraform.lock.hcl` pins each provider's hash; a run that would change one fails instead of silently accepting a different build. They were generated by CI, not by hand — there is no `tofu` binary in this environment, so **the only way to check infra changes here is to push and read the `Infra` workflow**. `fmt -check` and `validate` need no credentials and catch schema mistakes; `plan` cannot run until the account exists.
- `pnpm db:generate` / `pnpm db:migrate` — drizzle-kit against `packages/db`. `generate` needs no database and writes the next `migrations/NNNN_*.sql` from the schema; `migrate` applies them to `DATABASE_URL`. The dev stack's Postgres is `postgres://nekolog:nekolog@localhost:5432/nekolog_dev`. See `packages/db/README.md`.
- `pnpm load <ingest|api>` — drive one target with k6 (`internal/load`). It uses the k6 binary if it is installed and `grafana/k6` in Docker otherwise, checks `/health` before measuring anything, and takes `--vus`, `--duration`, `--events`, `--service`, `--url`, `--key` and `--runner`. Neither k6 nor Docker is needed for `pnpm test`. See `internal/load/README.md` for what it measured and what that changed.
- `pnpm self-host:up` — the first run of `deploy/self-host/`, from Node instead of `sh`: it writes `.env` with secrets from `node:crypto` (never overwriting one that is already there), reads each app's version from its own `package.json`, and runs `docker compose up -d --build`. `up.sh` stays for the machine, which has `openssl` and should not also need a toolchain; `internal/self-host/src/first-run.test.ts` fails if the two stop writing the same variables with the same defaults. This is what makes a first run work on Windows.
- `pnpm run release:sbom` — write one CycloneDX SBOM per published package into `sbom/` (gitignored) and check the set against the release; `pnpm run sbom:write` and `pnpm run sbom:check` are the two halves. CI runs it on every PR. See `internal/release/README.md`.
- `pnpm run licences:check` — pipe `pnpm -r licenses list --json` into `internal/release/src/licences-cli.ts` and fail on a dependency under GPL or AGPL. It runs in the `Supply chain` workflow next to `pnpm audit`.
- `pnpm tracking` — print what `internal/tracking` would create on GitHub from `docs/ETAPAS.md` (milestones, labels, one issue per step); `pnpm tracking -- --apply` actually creates it. Dry-run is the default because creating issues is public and cannot be undone in bulk, and the run is idempotent, so a new step in `ETAPAS.md` just needs another run. It never deletes, renames or closes anything. **It does rewrite the body of an open issue whose step drifted from `docs/ETAPAS.md`** — on 2026-11-03 all 53 open issues still said the PR closes them with `Closes #N`, which this repository cannot do. A closed issue is never touched (it is a record), an item ticked by hand survives the rewrite, and a lone tick is not treated as a change, so the next run cannot undo it. Do **not** run `--include-done` to "complete" the record: every M0/M1 step and 2.0 finished without an issue, and the flag would open 28 issues for work that is already merged, with no PR to link — which the README argues is a worse record than none. See `internal/tracking/README.md`.
- `pnpm changeset` — add a changeset for a package/app you just changed; `pnpm changeset:status` shows what's pending relative to `dev`.
- To run a single package's tests/typecheck directly: `cd packages/config && pnpm test` or `pnpm --filter @nekolog-io/config test`.

## Planned tooling (not yet present in the repo)

Two conventions hold there. ## Conventions

- **No comments.** This codebase is deliberately comment-free — the maintainer's explicit call, applied across the whole repo on 2026-10-30. Do not add explanatory comments, JSDoc, section banners, or `TODO`/`NOTE` markers to any `.ts`, `.tsx`, `.mjs`, `.js`, `.css`, `.yml`, or `.yaml` file. Put the explanation in a name, a smaller function, the commit message, the PR body, or a doc under `docs/` — not in the source. Two things are **not** comments and stay: compiler/tool directives (`// @ts-check`, `biome-ignore`, `eslint-disable`) and reference data (the `/* #hex */` annotations next to each OKLCH token in `globals.css`, which are the only record of the original palette values). Markdown prose is unaffected.
- **Relative imports carry the `.ts` extension** in everything Node loads directly — `internal/*`, `packages/*` and the Worker apps — because Node 24 runs this code with no bundler and will not resolve an extensionless specifier. (`apps/web` and `apps/docs` are the exception: Next and Astro bundle them, and neither is ever loaded as raw ESM.) TypeScript resolves it either way and vitest resolves it either way, so a package that gets this wrong looks fine until the first `node some/cli.ts` imports it — which is how `packages/adapters` shipped broken until step 1.13. A test that merely imports a module cannot catch this; `internal/seed/tests/cli.integration.test.ts` spawns a real `node` process, which can.
- **Commits:** Conventional Commits in English, scoped by package/app (e.g. `feat(core): add batching transport`, `fix(ingest): reject payloads above 512 KB`), enforced by commitlint (`npm-conventional` types only — `security/`-prefixed branches still commit as `chore(security): ...` or similar, not `security(...)`, since `security` isn't a valid commit type).
- **Branches:** one step from ETAPAS.md = one branch off `dev`, prefixed `feat/`, `fix/`, `chore/`, `docs/`, `ci/`, `test/`, `security/`, `infra/`, or `a11y/`. PRs into `dev` squash-merge; promotion `dev→qa→main` uses merge commits (no squash) so branches don't diverge. **This is enforced live, not just convention:** GitHub rulesets on `main`/`qa`/`dev` block deletion/force-push and require PRs + passing status checks (nobody has bypass, not even the repo owner), and `.github/workflows/branch-rules.yml` rejects PRs into `qa`/`main` from the wrong source branch. The `gh` CLI is set up and authenticated in this environment — prefer it (`gh pr create`, `gh pr checks --watch`, `gh pr merge --squash --delete-branch`) over raw GitHub API calls.
- **A step merges only when:** CI is green, new tests cover the change, a changeset exists if a package/app changed, UI strings exist in all three locales, docs are updated for anything public-facing, and (if labeled `security`) the security checklist was followed.
- **i18n:** landing page, docs, dashboard (in its own repo), emails, and README ship in pt-BR, en (source/fallback), and es. Code, commits, branches, and PRs are English-only. **This is enforced by tests, not just convention:** `apps/web/i18n/messages.test.ts` fails if a message key is missing, stale, or blank in any locale, and `apps/docs/tests/i18n-parity.test.ts` fails if a docs page lacks a translation (or a translation has no English source). Each app's locale list is a single exported constant (`apps/web/i18n/locales.ts`, `apps/docs/locales.mjs`) that both the app config and its test read, so adding a locale immediately makes the test demand translations.
- **Security is the top priority** (docs/PLANO.md §14): parameterized SQL only, permission checks server-side on every route/query, SSRF protections on alert webhooks, CSV export must guard against formula injection, PRs touching `apps/ingest`, `internal/db`, or permission-checking code get the `security` label and a dedicated review pass. **[docs/security/threat-model.md](docs/security/threat-model.md) is the working list** — it maps each threat to its mitigation and marks what's implemented vs. still planned, so when you build a feature, check which threats it's supposed to close. It also records what was accepted *without* full mitigation, so don't "fix" those without reading why. Operational procedures live in [docs/runbooks/](docs/runbooks/README.md); they describe the VPS as of 2026-11-05, and **none has been exercised** — there is no machine yet. `internal/self-host/src/runbooks.test.ts` is what keeps them from rotting: it fails if a procedure names a provider this platform stopped having, links to a file that does not exist, names a volume or ClickHouse role that is not declared, or mentions an environment variable nothing declares.
- **The dashboard comes back into this repository, and that was decided on 2026-11-06.** The two-repo split existed because this one was public and MIT; ADR [0017](docs/adr/0017-licenca-proprietaria-e-repositorio-privado.md) made it private and proprietary and left the consequence open — "a distribuição dos quatro pacotes compartilhados vira pergunta aberta", because `@nekolog-io/db` publishes its TypeScript **source** as its types and publishing it means handing the Postgres schema to anyone. `gabrielbarbosaa/nekolog-dashboard` is still **empty** (zero commits) and nothing was ever published to npm, so nothing has to be unwound. The dashboard becomes `apps/dashboard` here, `db`/`adapters`/`clickhouse`/`config` stop being publishable, and only the SDKs go to public npm. **The move, the ADR and the `ETAPAS.md` checkboxes for the 26 dashboard steps are their own step** — step 2.1 (`docs/ui-mockups/`) was built first, and deliberately carries no checkbox, because `internal/tracking` would open an issue for work already merged.

- **Logs are untrusted input** — anyone with a public key can send arbitrary text. Never render log content with `dangerouslySetInnerHTML`; escape everything.
- **The legal documents are typed data in `apps/web/content/legal/`, one module per locale, and they have not been reviewed by a lawyer.** They are rendered as text — never as HTML — and `content/legal/parity.test.ts` fails when a translation drops a clause, reorders a section, leaves an entry blank, lags behind on the `updated` date, or still carries the English sentence. Changing one locale means changing all three. - **The browser SDK puts the key in the URL on exactly one path, and that is not an oversight.** `navigator.sendBeacon` cannot send a header, so the `pagehide` flush posts to `/v1/logs?key=nekolog_pk_…` with a `text/plain` body — `application/json` would ask for a CORS preflight, and a preflight does not happen while the page is unloading (`apps/ingest`'s `ACCEPTED_CONTENT_TYPES` already allows both for this reason). Every other send keeps the key in `Authorization`. A **secret** key handed to `createLogger` is refused and nothing is sent: it would be a published credential, and `publicKeyOnly` has a test for it. The browser's `maxBatchBytes` is capped at 60 KB because that is the beacon's quota, and a refused beacon falls back to `fetch` with `keepalive` rather than losing the batch. `page.url` drops the query string and the fragment by default — reset tokens and invite codes live there. Its tests run against a real DOM (happy-dom) with `ErrorEvent`, `pagehide` and `visibilitychange` actually dispatched; a real browser is step 3.12.
- **Breadcrumbs ride on `error` and `fatal` only, as one 4 KB attribute, and that is forced by the payload contract.** Spec 1 has no breadcrumb field, so the trail travels as a `breadcrumbs` attribute in JSON; attaching 4 KB to each of 500 events would make a 2 MB batch the server refuses outright. `serialiseTrail` trims from the **oldest** end until it fits, never mid-record, so what arrives always parses. A click records `button#pay`, never the element's text or `value` — a label can name a person. Navigation and fetch addresses go through the same `page.url` stripping, the request body and headers are never read, and `ingestMatcher` skips the SDK's own batch so a flush does not become a breadcrumb of the next one. The two monkey-patches (`window.fetch`, `history.pushState`/`replaceState`) call through, return what the original returned, rethrow what it rejected, and restore **only if nobody patched after us**. XHR is deliberately not patched. A breadcrumb's `at` is an **ISO string, never milliseconds**: an epoch-millisecond value is 13 digits and roughly one in ten passes the Luhn check, so core's card filter replaced it with `[redacted]` outside the quotes and the whole trail stopped being JSON — with 20 crumbs that was near-certain, and `breadcrumbs.test.ts` walks 2 000 consecutive milliseconds in both forms to pin it. Note that core's redaction catches cards, CPF, `Bearer …` and nekolog keys but **not e-mail addresses** — that is core's scope, not an oversight here.
- **`traceparent` goes only where it was configured, and the matcher is deliberately strict.** The W3C spec lives in `packages/core/src/trace.ts` (`parseTraceparent`, `traceparentOf`, `traceForRequest`, `childSpan`, `createTraceTargetMatcher`); the browser, Node and `examples/express` all use it instead of three copies. `createTraceTargetMatcher` compares **whole host or whole origin**, never a text prefix — `api.shop.test` does not match `api.shop.test.evil.test`, a different port is a different origin, `http:` is not `https:`, a path entry must match at a segment boundary, and any scheme other than `http`/`https` is refused. The browser defaults to the page's own origin (a `traceId` is an internal identifier, and an extra header on a cross-origin request turns it into a preflight that can fail); the ingestion endpoint is skipped. **Node has no default at all**: `installTracePropagation({targets})` requires the list, because there is no "own origin" on a server and quietly sending internal ids to a payment gateway is not a default anyone wants. Adding the header never breaks the request — `Headers`, pair lists, plain objects and a prepared `Request` are each extended, not replaced, and anything unexpected sends the request *without* the header rather than not sending it. The browser uses **one** fetch patch for both breadcrumbs and the header (`installFetchPatch`), not two.
- **`nekolog init` refuses four things, and each has a test.** It never overwrites a variable the `.env` already holds (a real key is not replaced by a placeholder, nor by the one just passed to `--key`); it never puts a secret key in a `NEXT_PUBLIC_` variable, which ships in the bundle; it validates the key **before the first write**, so a bad `--key` leaves no half-written file; and it starts the package manager with `shell: false` and an argument list, with a test that pushes an `&` through and reads it back whole. `src/cli.ts` is only the shebang and `process.exitCode = await main(...)` — everything testable lives in `src/run.ts`, because importing the entry would otherwise run the CLI.
- **The 5 KB gzip budget for the browser SDK is not met, and the number is measured.** `init` is **12.05 kB gzip**, `createLogger` alone is **9.4 kB** (`packages/browser/.size-limit.json`, which runs in `lint`). `@nekolog-io/core` is 74% of that and is already tree-shaken — 40 kB of source becomes 17.5 kB in the bundle — and what remains is what the plan itself requires: the redaction pipeline with Luhn and CPF, the attribute flattener, retry with backoff, sampling. Reaching 5 kB would mean cutting the privacy filter, which is a §14 requirement. `size-limit` holds the numbers where they are so they cannot creep; the target itself is written up in `docs/PLANO.md` §9 as missed, with the measurement. **Do not raise these limits to make a build pass** — find the bytes or say so.
- **The compatibility matrix tests the built `dist`, not the source.** `internal/compat` bundles one `smoke.mjs` with every SDK inlined, and Node 22/24/26, Bun and Deno each run that one file — which is what a consumer actually gets. The browser job runs `src/**/*.browser.test.ts` through `@vitest/browser` and Playwright in Chromium, Firefox and WebKit; those files are **excluded** from the ordinary happy-dom run and hold only what a real browser can show (real `sessionStorage`, real `indexedDB`, real `navigator.sendBeacon`, the real `location`).
- **`examples/nestjs` runs from its build, and that is forced by Node.** Idiomatic Nest uses decorators, and Node 24's type stripping only erases types — it does not transform syntax — so this is the one example the Node runner cannot execute as `.ts`. It has a `tsdown` build and `start` runs `dist/main.mjs`, which is how a Nest app ships anyway, and `biome.json` enables `unsafeParameterDecoratorsEnabled` for that folder alone because `@Inject(...)` on a parameter is legacy-decorator syntax Biome does not parse by default. Its ClickHouse test refuses to run without the build rather than skipping quietly.
- **A Next route handler has no per-request context, and the example is where that is solved.** Express, Fastify, Hono and Nest each have a middleware that opens the `AsyncLocalStorage`; Next has no such hook — `instrumentation.ts` runs once per process and `proxy.ts` runs in another runtime — so `addContext` in a route handler had nowhere to write and the user id never appeared. `examples/next/app/api/with-nekolog.ts` opens the scope itself: continue the caller's `traceparent`, mint the `x-request-id`, return both as response headers, write the access line at the end. It lives in the example and not in the package because the right shape depends on the app.
- **The pino bridge is a destination, not a worker transport, and both bridges refuse to lose the message.** A pino `transport` runs in a worker thread, which would mean a second logger, a second queue and a second flush to get right at shutdown; a destination keeps the batching the service already has and lets `pino.multistream` go on writing to stdout. Both libraries carry a human line **and** a serialised error, and core's `buildEvent` takes the message from the error when the subject is error-like — so the bridges attach the error and keep the library's own line in a `log.msg` attribute when the two differ. Winston needs more care: `log.error('payment failed', err)` makes winston **concatenate** both into `info.message`, so the error's type and message come from the first line of `info.stack` instead, and the type is accepted only if it looks like an identifier. The winston transport reads the level from `Symbol.for('level')` (`info.level` may have been coloured by a format) and calls `next()` even when our logger throws, because a transport that does not call back stalls the chain.
- **The Nest interceptor opens the context around the *subscription*, and reads the error status from the error.** A Nest interceptor returns an Observable and the controller runs when something subscribes — after `intercept` has returned — so wrapping `next.handle()` in `runWithContext` leaves the handler outside the context; the interceptor returns a new `Observable` and subscribes inside the scope. And Nest's exception filter has **not** set `response.statusCode` when the interceptor is told about a thrown error, so the error path reads `HttpException.getStatus()` or a `status` field instead — reading the response logged a 500 as `info`, which an end-to-end test caught. The package deliberately uses **no decorator syntax**, so it compiles without `experimentalDecorators`/`emitDecoratorMetadata`; a `Module({})(NekologModule)` call was removed after the sabotage harness proved it defines no metadata at all (Nest's `Module` writes one key per property of the object it is given, and `{}` has none).
- **The three server middlewares share one implementation, in `@nekolog-io/node`'s `src/http.ts`.** `startRequest` continues the caller's trace, validates or mints the request id and returns the response headers; `levelForStatus`, `requestIdFrom` and the access line live there too. An incoming `x-request-id` is accepted only as up to 64 characters of `[A-Za-z0-9._:-]` — it goes straight back out in a response header, so trusting it would be letting the client write one. The access line names the **route pattern**, never the address. Three things are easy to undo by accident: Express wraps the `finish` listener in `bindContext` (an event listener does not inherit the registrant's `AsyncLocalStorage`, and the only test that can tell fires `finish` from outside the context on purpose); Hono records in a `finally` so a middleware further down that throws still gets its line, which `app.request()` cannot show because Hono catches handler errors itself — the test calls the middleware directly with a rejecting `next`; and the Fastify plugin carries `Symbol.for('skip-override')` or its hooks would be encapsulated in the `register` scope and log nothing, and it calls `done()` **inside** `runWithContext` so the context reaches the handler. `withErrorLog` logs and calls `next(error)`: the error response is the app's to decide, and our logging failing must not swallow the app's error.
- **`@nekolog-io/next` has two entries and that is load-bearing.** The root entry is server-side and pulls `node:async_hooks` through `@nekolog-io/node`; `@nekolog-io/next/client` is `'use client'` and imports nothing from Node. `register()` builds one logger per process however many times Next calls `instrumentation.ts`, uses the Node logger with process hooks on `nodejs` and a core logger with `runtime: 'edge'` and no hooks on `edge`, and treats an unknown `NEXT_RUNTIME` as `nodejs` rather than believing it. `onRequestError` records the path without its query, the method and the Next routing fields, and **never the headers** — session cookie, `Authorization` — and never throws back into Next when our own logger fails. Its `attw` runs with `--profile node16` because node10 cannot resolve a subpath export and Next needs Node 18 anyway.
- **The React provider does not own the client, the page does.** 
ekologClient() is a module-level singleton, so two nested NekologProviders, StrictMode's double render and a route that unmounts and remounts all share one client with the global handlers installed once — and unmounting the provider closes nothing, because the page is still the page. closeClient() exists for tests and for an app that really is ending. `useLogger` outside a provider returns a console-backed logger and warns once instead of throwing: React's convention is to throw, but this SDK must never throw into the host app, and a forgotten provider cannot be why a production page goes blank. The boundary's `onError` runs in a `finally`, so a logger that throws cannot take the app's own handler down with it.
- **The offline queue parks only a transport failure, and never writes the key.** `parkingSender` catches a rejected `fetch` — what "no network" looks like — and puts the batch in IndexedDB; a `400` is a refusal the server will repeat, so it passes through and the batch is dropped rather than retried forever. On replay, `429`/`5xx` keep a batch and `4xx` deletes it. The stored record is `{at, url, body}` only: the `Authorization` header is rebuilt from the live key, because a key in a browser database is a credential at rest for nothing, and a test asserts the record has no other field. At most 50 batches, 2 MB and 7 days, oldest out first. If IndexedDB refuses, the **original** error is rethrown instead of a fake 202 — and `within()` awaits the transaction's completion for the same reason: an `add` that succeeded inside a transaction that then aborted (quota) is not a saved batch. `installOnlineReplay` runs once at install, which is what makes the error that happened offline arrive on the next visit.
- **`lint` depends on `["build", "^build"]` — both edges, and both are load-bearing — and no `lint` script rebuilds.** With `dependsOn: ["^build"]` alone, Turbo could run `pkg#build` and `pkg#lint` at the same time and the pack would find an empty `dist/`, which is how `@nekolog-io/clickhouse` failed CI once the browser package changed the scheduling; dropping the `^build` edge instead broke `examples/react-vite`, which bundles `@nekolog-io/react` and found no dist. Those edges were not enough on their own. Every published `lint` script used to start with `pnpm run build &&`, so the build ran **twice** — once by Turbo and once inside the script — and tsdown cleans `dist/` first, so that second build could empty a package's `dist/` while a **sibling's** lint was reading it. `^build` orders a dependency's build against a dependent's lint; nothing orders two packages' lints against each other. That is how `@examples/next` failed to resolve `@nekolog-io/next` on 2026-11-04. The `pnpm run build &&` prefix is gone from all sixteen scripts: Turbo's `dependsOn: ["build"]` already guarantees a current `dist/`, so nothing cleans during lint any more. The cost is that `pnpm --filter X lint` on its own now assumes `dist/` exists — run `pnpm lint` (which goes through Turbo) or build first. **Neither failure reproduces locally**: turbo orders tasks differently depending on core count, so CI is the only place this shows.
- **An issue's three rules live in the store, and the issue rollup windows by `received_at`.** `first_seen_at` never moves forward and `last_seen_at` never moves backward (`least`/`greatest` in the `on conflict`), because a late batch arrives out of order; a **resolved** issue that happens again reopens and gets `regressed_at`, but only when the occurrence is newer than the fix, so a batch from before the deploy cannot undo it; an **ignored** one never reopens. The rollup groups by `received_at`, never the client's `timestamp` — the same reason as `usage_per_minute` and the quota (threat T7), since a sender that backdates its events would fall outside every window and never be grouped — while `first_seen`/`last_seen` still come from `timestamp`, which is what people read. The `fingerprint` is **text everywhere**: a `UInt64` does not fit in a JavaScript number, so `18446744073709551615` has to survive ClickHouse, the store and the Postgres column unchanged. One ClickHouse trap: the rollup's `WHERE` must be qualified (`logs.fingerprint != 0`), because the `SELECT` has a `fingerprint` alias of type `String` and ClickHouse resolves the alias, then refuses to compare it with `0`.
- **The fingerprint hashes its own version, and `rowsFor` is async because of it.** `fingerprint_v1` and the rule name are the first two parts of the text that becomes the SHA-256, which is what makes an algorithm change open new issues instead of merging into the old ones, and what keeps a stack fingerprint from colliding with a message one. Four tests pin each rule's output to a literal number, so the algorithm cannot drift unnoticed. The value is written as a **decimal string**, because a real `UInt64` does not fit in a JavaScript `number` and ClickHouse accepts a quoted one in `JSONEachRow`; `0` still means "no fingerprint". `crypto.subtle.digest` is async, so `rowsFor` returns a promise now — don't "simplify" that back. Two things that cost real time: the **first line of a Chrome stack** (`TypeError: … (reading 'id')`) ends in a bracket and was being read as a frame, so a location is only accepted when it has no whitespace and either holds a slash or ends in `:line:column`; and `normaliseMessage` only looks at the first **1024 characters**, because the e-mail pattern is quadratic on input like `a@a@a@…` and seven hostile 16 KB messages took **287 ms** — on a Worker with a 10 ms CPU budget that is the ingestion stopping.
- **A rotation overlaps two secrets and never three, and the database key can only be rotated through `resealChannelSecrets`.** While `previous_sealed_secret` is set, `X-NekoLog-Signature` carries two signatures separated by a comma, **current first** — the shape Stripe and GitHub use, so a receiver checking either keeps working. Sending more than two is refused, because a window that accumulates is a window nobody closes. `resealChannelSecrets` opens every sealed secret with the old key and writes it back under the new one; the rotation runbook had recorded the absence of exactly this as a real pending item, with "rotating this key today, without it, destroys data". Three things make it safe against production: a **dry run** opens everything and writes nothing, so an old key that does not open some row is found before anything is lost; running it **twice is harmless**, because a secret already on the new key is recognised and left alone, which is what lets an interrupted run resume; and each write lands **only if the row is still as it was read**. A secret it cannot open is reported, never wiped.
- **An operator alert is written to the log whether or not it was delivered, and never throws back.** The capacity, quota and spool signals go to `OPS_DISCORD_WEBHOOK_URL` through the **same** SSRF guard, `redirect: 'manual'` and five-second deadline as a tenant's webhook — an operator channel is still an address somebody typed. Severity follows the rule the rest of the codebase already uses: **"I cannot measure" is critical**, because a disk reading that failed is not a healthy disk, and a batch replayed but **not deleted** is critical because the next run writes it again. An environment let back in after a block raises nothing, and a batch that replayed as intended raises nothing. `OPS_DISCORD_WEBHOOK_URL` and `HEARTBEAT_URL` are **secrets**, not configuration: each is a URL anyone holding it can post to, so they live in the machine's `.env` and never in a committed file.
- **Server-side redaction takes named patterns, never a tenant's regex, and fails closed.** `environments.redaction_rules` turns on patterns from a **closed list** (e-mail, IPv4, IPv6, Brazilian phone, CPF, CNPJ, JWT, `Bearer`, UUID, credit card) and blanks attributes by exact key or by prefix; a check constraint refuses a key called `regex`, `pattern` or `patternSource`. That is not bureaucracy: a third party's regular expression on the hot path of a Worker with a 10 ms CPU budget is denial of service the user writes for you. **It happened again here anyway** — the first e-mail pattern took **266 ms** over 16 KB of `1-1-1-…`, because `[A-Za-z0-9._%+-]+@` backtracks the whole run from every start position; bounding the local part to 64 characters (RFC 5321's own limit) took it to 9.2 ms, and all ten together now cost 5.8 ms on the worst shape measured, with a test pinning the budget. A stored rule that **cannot be parsed applies every pattern** rather than none: a privacy control that quietly stops working is worse than one that over-redacts. Redaction runs over the message, the stack trace and every attribute value, and `String.replace` with a `/g` regex resets `lastIndex` itself, so no reset line is needed (one was there and was dead).
- **The self-host spool and block list are files, and that is forced by the same rule as everything else.** `@internal/self-host`'s `fileBlobStore` and `fileKvNamespace` stand in for R2 and Workers KV on one machine, through two Docker volumes the ingestion and the jobs share. Postgres is the obvious choice and the wrong one: **the ingestion never depends on Postgres or Redis**, and the ingestion is what writes the spool and reads the block list. Both write a `.writing-<random>` file and `rename` it into place, because a reader polling the spool that picks up half an envelope quarantines a batch that was never broken; `list` skips every dotted name and no key may start with one. A blob key is an allowlist, `[A-Za-z0-9][A-Za-z0-9._-]*` per segment, since half of a spool key is a `batchId` the client chose. The mounts are deliberately asymmetric — `ingest` holds the KV and the seed read-only, only `jobs` writes the KV, only `bootstrap` writes the seed — and `internal/self-host/src/compose.test.ts` fails if that changes. **The self-host jobs container runs more tasks than the Worker**: a Worker cannot reach Postgres, so `alert-evaluate`, `alert-notify` and `issue-rollup` are wired only here, which is why `DATABASE_URL`, `ENCRYPTION_KEY` and `NEKOLOG_CONSOLE_URL` are required rather than optional — starting without them would mean silently evaluating no alerts. Exports are **not** wired: 4.12 writes through ClickHouse into S3 and reading one back needs credentials this stack never asks for, so the self-host ClickHouse user has no grant on S3 at all. Two image details that cost time: the root `prepare` script runs `lefthook install`, which needs a git repository, so the Dockerfile deletes that one script rather than shipping `.git`; and `COREPACK_HOME` plus `corepack install` at build time are what keep a container start from downloading pnpm over the network.
- **The public read API scopes on the key, refuses `?key=`, and only reads.** A `sk_` key names one project and one environment, so `apps/api` passes exactly those to `searchWhere` and `sqlIssueReader`; a caller's `?project=` changes nothing and `env:` inside the search is **refused with a 400** rather than ignored, because a filter that silently does nothing reads like a filter that works. A request carrying `?key=` is turned away before anything else is read — even a blank one, even alongside a valid header: the ingestion's `?key=` path exists only because `sendBeacon` cannot send a header while a page unloads, and nothing here is a beacon. A **public** key is refused too, since it ships in every browser. Only `GET` is routed, so a `POST` to `/v1/logs` is a 404 and not a method error, and the ClickHouse credential is `nekolog_reader` — `SELECT` on one database, no S3 and no `system`. A failed upstream query answers `503 upstream_unavailable` with a fixed sentence; the real exception can quote a column or a bound value, so it goes to the log instead. **`DATABASE_URL` is required, not optional**: `issues` lives in Postgres, and starting without it would mean an API that 404s on a third of its routes and never says why. On Workers that Postgres is reached over HTTP with Neon's driver behind the same `SqlRunner` the Node entry fills with `postgres`, which is the only reason a Worker can serve issues.
- **The one route that writes asks for a different scope, and the CLI refuses three things before it opens a socket.** `POST /v1/releases` needs `logs:write`; everything else is a `GET` needing `logs:read`, so a `GET` on `/v1/releases` is a 404 just as a `POST` on `/v1/logs` is. `logs:write` is deliberately **not** enough on its own: a check constraint forces a *public* key to be exactly `['logs:write']`, so the route refuses a public key by its prefix first — otherwise a key published in every browser bundle could rewrite release history. Recording is **idempotent**: `on conflict (environment_id, version)` keeps the earliest `released_at` with `least` and the known commit with `coalesce`, because a pipeline that reruns is neither a new deploy nor a failure. `nekolog releases create` mirrors the refusals client-side — a public key, a commit that is not what `git rev-parse` prints, and plain HTTP to anything but a loopback host — so a mistyped flag never puts a secret key on the wire. The CLI has **zero runtime dependencies**, so `COMMIT_PATTERN` and `MAX_VERSION_CHARS` are duplicated there and `releases.test.ts` compares both against `@nekolog-io/adapters`, the same arrangement as `packages/core/src/limits.ts`.
- **A source map is stored through `BlobStore`, keyed by the release id, and checked rather than parsed.** The self-host gets a directory and Cloudflare gets an R2 bucket from the same code, which is why this works where **exports** could not: an export is written by ClickHouse itself (`INSERT INTO FUNCTION s3(...)`), which cannot reach a directory the app controls, whereas a source map arrives as bytes in a request. The key is `sourcemaps/<projectId>/<releaseId>/<name>` and uses the **release id, never the version** — `releases_version_shape` allows any trimmed 1–200 characters, so a version may legally hold `/` or `+`, while an id is `rel_` plus Crockford by construction. The name is one segment matching `^[A-Za-z0-9][A-Za-z0-9._-]*\.map$`, so `../`, a slash, a leading dot and a non-map extension are all refused. **The body is checked, not parsed**: the first 4 KB must open a JSON object and name `mappings` or `sections`, and a declared `version` must be 3 — parsing megabytes of JSON does not fit a Worker's CPU budget, and 4.10 parses the map where it is used. An upload must name a release that **already exists**, so `releases.sourcemap_count` cannot drift, and re-uploading a name replaces it without raising the count. `headOf` reads the head as Latin-1 on purpose: `packages/adapters` has `types: []` so there is no `TextDecoder`, and a UTF-8 continuation byte is never ASCII, so searching for ASCII keys is still correct.
- **The bundler plugin has only `writeBundle`, and that is the whole security argument.** `@nekolog-io/bundler-plugin` holds a *secret* key inside a build whose output ships to browsers, so it deliberately carries no `transform`, `load` or `resolveId` — it cannot write anything into the bundle it is uploading maps for, and `plugin.test.ts` fails if one of those hooks appears. The rest follows two rules: with **no key** it does nothing and prints one line (that is a local build, and failing over it would be unbearable), and with a key **anything else wrong fails the build**, because a release recorded without its maps is the exact problem the feature exists to prevent. - **The Worker's 10 ms of CPU is the tightest limit in the project, and k6 cannot see it.** Step 6.4 measured the biggest batch specification 1 allows (500 events, 20% errors, gzipped, every redaction rule on) at **10.8 ms** — it did not fit, and nothing caught it because k6 measures latency, behind which a CPU limit hides. - **`queryRows` asks ClickHouse to quote 64-bit integers, and removing that silently corrupts fingerprints.** A `UInt64` does not fit in a JavaScript number. - **OTLP is translated into specification 1 before anything else, and answers `200`, not `202`.** `POST /v1/otlp/logs` converts the body first, so an OTLP record goes through the same validation, fingerprinting, minimum level, sampling and redaction as a native one — there is no second ingestion path to keep in step. The response shape is the OTLP one (`{ partialSuccess }` with `rejectedLogRecords`), because an exporter reads a `202` or a foreign body as a failure and retries. **`timeUnixNano` is read with `BigInt`**: it has exceeded `Number.MAX_SAFE_INTEGER` since 2001, and the float path silently rounds a millisecond away — `1762257600999999999` becomes `…601000` instead of `…600999`, which after 4.11 decides which partition the row lands in. - **The minimum level and the sample rate are enforced at the ingestion, and sampling is seeded on the trace.** They are columns on `environments` that ride on the `KeyRecord` into KV, so the Worker reads them without touching Postgres — a screen cannot stop a write, so this cannot be a screen setting. The sample seed is the `traceId`, then the session id, then the event's place in its batch, so **a whole trace is kept or dropped together**; sampling event by event would leave half a trace, which is no use to anybody investigating. **`error` and `fatal` are never sampled out**, whatever the rate — a rate set low to control volume should cut the noise, not the signal. - **An alert's history is written in the same statement that moves the rule, and the cooldown holds back only a firing notice.** `applyTransitions` is one CTE: it updates `alert_rules` and inserts into `alert_events` together, so a run that dies between the two cannot exist, and `on conflict (rule_id, at) do nothing` makes a replay harmless. The cooldown counts from **the last firing notice that actually went out** — an `alert_events` row with `state = 'firing'` and `notified_at` set — not from the last transition and not from the last notice of any kind. It never holds the all-clear: being told something broke and never told it was fixed is worse than one message too many. A held-back alert is recorded with `suppressed = 'cooldown'` **and** stamped as notified, so it is not weighed again every minute. Specification 6 says the states are `ok → firing → resolved`; the enum has **two** values, because "resolved" is the return to `ok`, and the spec carries that correction. - **An alert channel's address is checked for SSRF twice, and its secret is bound to its row.** `assertWebhookTarget` refuses anything but `https` on port 443, an address carrying credentials, `localhost`, `*.local`, `*.internal`, `*.lan`, `*.home.arpa`, `*.in-addr.arpa`, the cloud metadata hosts, a **bare name with no dot** (which can only exist on this network), and every private or reserved IPv4 and IPv6 range. - **A scheduled export always exports the period that *closed*, and the notice carries nothing anybody typed.** `windowFor` returns the previous UTC day or the previous Monday-to-Monday week, never the period in progress, and the task waits fifteen minutes past the boundary so late logs still land inside it. - **The export is generated by ClickHouse, and four of its details were measured rather than assumed.** `compileExport` builds `INSERT INTO FUNCTION s3(...) - **The stored `timestamp` is bounded, because `logs` partitions and expires by it and it belongs to the client.** A clock set further back than the retention makes ClickHouse **drop the row at the insert** — the partition appears with zero rows and nothing is reported, which is how a whole service can log into the void. A clock set forward writes into a partition no period query reaches and whose `TTL` only expires after it, so the retention a tenant pays for never applies (threat T10). `boundedTimestampMs` therefore clamps to `[received_at - (retention_days - 1h), received_at + 5min]`: the hour of margin keeps a merge from eating the row moments later, the floor follows the **environment's own** retention rather than a fixed window (so the browser's seven-day offline replay is untouched on a thirty-day retention but rescued on a one-day one), and the five minutes ahead leave ordinary NTP drift alone. `clock_skew_ms` records the **real** distance either way, so the original is exactly `received_at - clock_skew_ms`. - **A number in the documentation is pinned to the constant that enforces it.** The four docs tests count files, resolve links and check the sidebar — none of them can see a page that states the wrong limit. `apps/api/src/documented.test.ts` reads `api/reference` and `api/search` **in all three locales** and fails if they drift from the code: every `API_ERROR_CODES` value with its status, every parameter each route takes, every histogram bucket, every `SEARCH_FIELDS` entry, and the numbers (1000 rows, 200 issues, 1500 points, 120 requests a minute, 31 days, 8 MB, 200 maps, and the search language's 1000/20/5). It lives in `apps/api` rather than `apps/docs` because the app owns those constants and an app may not depend on another app.
- **The docs guides are checked by four tests, and page parity is the weakest of them.** `apps/docs/tests/i18n-parity.test.ts` only counts files, so it cannot see a broken link, a page nobody can navigate to, or a "translation" that is still in English. `tests/links.test.ts` resolves every internal `/docs/…` link against the pages that exist, refuses a link that leaves its own locale (which is also what catches a page copied from the English source and never translated — the copy brings the English links with it), and requires every guide to be linked from the quickstart of its own locale. `tests/guides.test.ts` requires every page to appear in the sidebar of `astro.config.mjs` (a slug with no page already fails the build; a **page with no slug** builds fine and is reachable only by typing the URL) and requires every server guide, in all three locales, to tell the reader to allow `traceparent` in CORS — that note is the whole point of step 3.15, because without it the browser's `traceparent` turns a cross-origin call into a preflight the API refuses. `tsconfig.scripts.json` covers the whole `tests/` directory and needs `allowJs` for `locales.mjs`. Don't narrow it back to one file.
- **The security headers come from `internal/security-headers`, and `script-src` has no opt-out.** `apps/web` builds a nonce per response in `proxy.ts` (Next 16 renamed `middleware.ts` to `proxy.ts`; the exported function must be called `proxy`), and `apps/docs` — static, so no per-request nonce exists — carries a hash per inline script in a **generated** `apps/docs/vercel.json`. Its `build` fails when that file stops covering what the build produced; regenerate with `pnpm --filter @apps/docs headers:write`. Two things are easy to undo by accident: the docs' `style-src 'unsafe-inline'` is there because Starlight writes hundreds of `style="…"` attributes, which no hash or nonce reaches, and the generator **refuses** to emit a policy when a `<style>` element appears, because a hash there makes the browser ignore `'unsafe-inline'` and breaks all of them silently. `apps/web` writes no style attribute and a test fails if one appears. CI now runs **Build before Test**, because `WEB_HEADERS_TEST_REQUIRED` and `DOCS_HEADERS_TEST_REQUIRED` turn a missing build into a failure instead of a skip.
